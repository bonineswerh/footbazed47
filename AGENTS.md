# FOOTBAZED: правила работы с проектом

Этот файл действует для всего репозитория. Он описывает фактическую архитектуру FOOTBAZED и обязательные правила для всех последующих изменений. Если архитектура проекта меняется, обновляй этот файл в том же изменении.

## 1. Назначение продукта

- FOOTBAZED — русскоязычная футбольная платформа, где болельщики оценивают завершённые матчи и игроков, ведут профиль, публикуют оценки, обсуждают матчи и взаимодействуют с друзьями.
- Основные публичные сущности: матчи, клубы, игроки, пользовательские профили и публичные оценки.
- Основные авторизованные сценарии: создание профиля, оценки матчей и игроков, прогнозы, друзья, сравнение вкусов, реакции, комментарии, уведомления, чат матча и личные чаты друзей.
- Администрирование встроено в основное приложение и доступно через `/admin`; `admin.html` существует только как `noindex`-редирект для старых ссылок.
- Продукт сейчас футбольный. Не обобщай доменную модель под другие виды спорта без отдельного архитектурного решения.

## 2. Подтверждённый стек

- Runtime-клиент — статическое SPA на HTML, CSS и обычном JavaScript без frontend-фреймворка, сборщика и компонентного runtime. TypeScript используется для сгенерированного контракта БД и CI-typecheck, но пока не исполняется в браузере.
- Навигация — History API с индексируемыми путями `/club/<id>`, `/player/<id>`, `/match/<id>`, `/profile/<uuid>` и статическими разделами. Старые hash-маршруты остаются только для обратной совместимости; маршрутизацией управляют `go`, `syncRoute` и `applyRouteFromLocation` в `app.js`.
- Данные, Auth и PostgreSQL — Supabase через `@supabase/supabase-js@2`.
- Серверная часть — CommonJS Vercel Functions: `api/config.js` для публичной runtime-конфигурации, `api/admin.js` для привилегированных действий и `api/sitemap.js` для динамического sitemap.
- Внешние футбольные данные — football-data.org, доступный только из `api/admin.js`.
- Production — Vercel из GitHub-ветки `main`.
- Тесты — встроенный `node:test`, pgTAP и Playwright Test с Axe. Требуется Node.js 22+.
- Менеджер зависимостей — pnpm: изменяя зависимости, обновляй и коммить `pnpm-lock.yaml`; не добавляй параллельный `package-lock.json`.

Не добавляй новый фреймворк, bundler, state manager, ORM или серверный слой только ради удобства отдельной функции. Такое изменение требует доказанной пользы для всего проекта и отдельного согласованного этапа миграции.

## 3. Карта ответственности файлов

- `index.html` — статическая оболочка страниц, навигация, доступные диалоги и порядок подключения клиентских скриптов.
- `styles.css` — дизайн-токены, общие компоненты, темы и основная адаптивность.
- `css/entities.css`, `css/feed.css`, `css/messages.css`, `admin.css` — стили соответствующих доменов.
- `app.js` — иконки, общий shell, маршрутизация и существующие общие сценарии профиля, друзей, уведомлений, шаринга и настроек.
- `js/core.js` — инициализация публичного Supabase-клиента из runtime-конфигурации, разрешённые наборы полей, кэш и функции безопасного вывода.
- `js/data.js` — единая клиентская граница агрегирующих и пагинированных RPC.
- `js/seo.js` — canonical, metadata и structured data для маршрутов.
- `js/session-hint.js` и `js/performance.js` — безопасная ранняя стабилизация layout и сбор LCP/CLS/INP без пользовательских данных и сетевой отправки.
- `js/domain.js` — чистая доменная логика, доступная и браузеру, и `node:test`.
- `js/auth.js`, `js/ratings.js`, `js/matches.js`, `js/entities.js`, `js/feed.js`, `js/messages.js`, `js/search.js`, `js/admin.js` — владельцы своих доменов. `js/rating-loader.js` сохраняет глобальный `openRate()` и лениво подключает `js/ratings.js`; `js/messages.js` лениво загружается при открытии личного чата. Не возвращай эти модули в критический путь главной страницы.
- `js/appearance.js`, `js/overlays.js`, `js/confirm.js`, `js/account.js` — общие UI-механизмы.
- `api/admin.js` и `api/sitemap.js` — доверенные серверные границы с `service_role`; ключ никогда не передаётся клиенту.
- `supabase/migrations/` — полная последовательная история production-схемы, воспроизводимая на пустой локальной БД.
- `types/database.ts` — генерируемый Supabase-контракт. Не редактируй вручную; CI сравнивает его с чистой БД после всех миграций.
- `tests/domain.test.js` — unit-тесты чистой логики.
- `tests/e2e/` — детерминированные авторизованные браузерные сценарии без записи в production.

## 4. Архитектурные правила

- Не раздувай `app.js` новой крупной доменной логикой. Новые самостоятельные функции размещай в отдельном `js/<domain>.js` и экспортируй одним пространством имён `window.FBZ<Domain>`.
- Новые клиентские доменные модули оформляй как IIFE с `'use strict'`, закрытым состоянием и минимальным публичным API. Существующие глобальные функции сохраняются для совместимости с inline-обработчиками.
- Чистые правила валидации, сортировки и нормализации размещай в `js/domain.js`, чтобы их можно было тестировать без DOM и Supabase.
- Порядок стартовых `<script>` в `index.html` является контрактом зависимостей. `domain.js`, appearance/core и общие UI-модули должны быть загружены до кода, который их вызывает. `feed`, `entities`, `messages` и `admin` загружаются только через `ensureFeatureModule`; не возвращай их в стартовый HTML.
- Для изменённого CSS или клиентского JS обновляй query-версию соответствующего `src`/`href` в `index.html`, чтобы Vercel и браузеры не оставляли устаревший asset.
- Не создавай вторую систему маршрутизации. Новые ссылки используют красивые пути без hash; парсинг старых hash-ссылок сохраняется до отдельной совместимой миграции.
- Не создавай отдельную админку или отдельную модель авторизации: административный интерфейс остаётся страницей основного SPA, а реальная авторизация выполняется сервером.

## 5. Frontend conventions

- Пользовательский текст — на русском языке; бренд всегда отображается как `FOOTBAZED`.
- При создании HTML из строк экранируй каждый пользовательский и внешний текст через `esc()`.
- Значения, встраиваемые в inline JavaScript-атрибуты, пропускай через `jsStr()`. Не собирай такие аргументы простой конкатенацией.
- Внешние и пользовательские изображения пропускай через `safeImageUrl()`. Для `<img>` используй подходящие `alt`, `loading` и `decoding`.
- Для простого текста предпочитай `textContent`; `innerHTML` допустим только для контролируемого шаблона с экранированными значениями.
- Не показывай пользователю необработанные сообщения Supabase, Auth, PostgreSQL или внешнего API. Локализуй ожидаемые ошибки и выводи безопасный fallback.
- У любой async-команды должны быть состояния loading/disabled, обработка ошибки и восстановление кнопки в `finally`.
- Для запросов, результат которых может устареть, применяй версию запроса или другой механизм отмены, как в поиске, ленте и страницах сущностей.
- Используй существующие `FBZOverlay`, `FBZConfirm`, `toast`, `ico`, `copyText`, `getCache`/`setCache`; не создавай параллельные реализации модалок, подтверждений, уведомлений или кэша.
- Новые иконки добавляй в существующий реестр `I` и получай через `ico()`. Не размножай произвольные inline SVG по шаблонам.
- Не сохраняй access token, пароль, email или другие чувствительные данные в пользовательские ключи `localStorage`. Текущий local storage предназначен для внешнего вида, недавних запросов и некритичного кэша `fb_*`.

## 6. Backend conventions

- `api/admin.js` остаётся CommonJS Vercel Function и возвращает JSON с `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.
- Каждый административный запрос обязан передавать Supabase access token в `Authorization: Bearer ...`.
- Сервер обязан самостоятельно проверить token через Supabase Auth и затем проверить `users.is_admin`. Проверка `CU.is_admin` на клиенте — только UX, не авторизация.
- `SUPABASE_SERVICE_ROLE_KEY` используется только на сервере и только после успешной проверки администратора.
- Все действия API должны находиться в явном allowlist, проверять method, типы, диапазоны, даты и перечисления. Сохраняй ограничение тела запроса и timeout внешнего API.
- Ошибки 500 не должны раскрывать детали базы, ключи, SQL или upstream response. Подробности допустимы только в server log.
- football-data.org вызывается только сервером. Не передавай `FOOTBALL_DATA_API_KEY` в клиент и не вызывай внешний API напрямую из браузера.
- Синхронизация должна быть идемпотентной: внешние сущности связываются по `external_id`, игроки — по существующему уникальному контракту, upsert не должен создавать дубликаты.

## 7. Supabase и Data API

- Публичный anon/publishable key допустим в клиенте; secret/service-role key — никогда.
- RLS и SQL grants — независимые уровни. Для доступной через Data API таблицы должны быть одновременно настроены необходимые grants и корректные RLS policies.
- Используй минимальные grants. Для `users` сохраняй column-level доступ: публично читаются только поля из `PUBLIC_USER_FIELDS`; `email`, `invite_code` и `is_admin` не раскрываются, а агрегаты `ratings_count`, `avg_rating`, `streak`, `streak_date` доступны для чтения, но не для клиентской записи.
- Собственный полный профиль загружается через `get_my_profile`; email берётся из Supabase Auth session, а не из публичного `users`-select.
- Клиент может обновлять в `notifications` только колонку `read`. Создание уведомлений выполняют серверные triggers/functions.
- Оценки матчей и игроков изменяются только через `save_match_rating` и `delete_match_rating`.
- Чат матча изменяется только через `send_match_chat_message` и `edit_match_chat_message`. Личные беседы и сообщения изменяются только через RPC `get_or_create_direct_conversation`, `send_direct_message` и `edit_direct_message`.
- Лайки и комментарии оценок изменяются только через `toggle_rating_like`, `add_rating_comment` и `delete_rating_comment`.
- Не возвращай в RPC лишние колонки. Публичные агрегаты должны отдавать минимальный готовый payload, как `get_social_feed_page`, `get_club_page`, `get_player_page` и `get_match_insights`.
- Для независимых публичных чтений предпочитай `SECURITY INVOKER`. `SECURITY DEFINER` допустим только для подтверждённой серверной операции или безопасного агрегата, которому нужен контролируемый обход RLS.
- Любая `SECURITY DEFINER` function обязана иметь `set search_path = ''`, schema-qualified объекты, проверку `auth.uid()`/владения для мутаций, строгую валидацию и явные `REVOKE`/`GRANT EXECUTE`.
- Trigger-functions не должны быть напрямую доступны `anon` или `authenticated`.
- После изменения функций или grants выполняй `notify pgrst, 'reload schema'`, если PostgREST должен перечитать контракт.

## 8. Правила RLS

- RLS обязателен для каждой таблицы в exposed schema `public`, включая новые таблицы.
- Не используй `TO authenticated` как достаточную авторизацию. Политика должна ограничивать строки по `auth.uid()`, владельцу, адресату, публичности или подтверждённой дружбе.
- Для UPDATE всегда задавай и `USING`, и `WITH CHECK`, чтобы владелец не мог перепривязать запись другому пользователю.
- Для INSERT пользовательский идентификатор должен совпадать с `(select auth.uid())`; не доверяй `user_id` из браузера без policy/function проверки.
- Публичная оценка доступна всем, приватная — только её автору. Player ratings, likes и comments должны наследовать видимость родительской оценки.
- Профиль видим, если он публичный, принадлежит текущему пользователю или доступен подтверждённому другу. Не обходи `is_user_visible` прямым широким users-select.
- Дружба двусторонняя по чтению, но запрос создаёт отправитель, а pending-запрос принимает или отклоняет только адресат.
- Личная беседа и её сообщения доступны только двум участникам при действующей подтверждённой дружбе. Прекращение дружбы немедленно закрывает чтение, отправку и доступ к вложениям.
- Уведомления читает и помечает прочитанными только их получатель.
- Проверяй политики минимум как `anon`, пользователь-владелец и другой `authenticated` пользователь. Проверка только под `service_role` ничего не доказывает, потому что он обходит RLS.

## 9. Database conventions

- SQL-имена — `snake_case`; таблицы во множественном числе; foreign keys заканчиваются на `_id`; внешние провайдерские IDs хранятся отдельно как `external_id`.
- Пользовательская identity — UUID из `auth.users`. Футбольные сущности используют существующие bigint identity IDs.
- Новые даты событий храни в `timestamptz`, если нет доказанной причины для другого типа.
- Инварианты закрепляй на уровне БД через `NOT NULL`, `CHECK`, `UNIQUE` и foreign keys, а не только через форму.
- Для удаления выбирай осознанную семантику: зависимые пользовательские детали оценки удаляются cascade; исторические ссылки на клуб допускают `SET NULL`.
- Индексируй foreign keys и реальные пути поиска/фильтрации/сортировки. Для частых подмножеств предпочитай частичные индексы, как уникальные best-player и notification indexes.
- Любой потенциально многозаписный ответ должен иметь серверный limit. Лента использует cursor pagination; матчи временно используют bounded offset pagination через `get_matches_page`.
- Не создавай N+1-запросы ради карточек. Сложные страницы и лента должны получать агрегированный payload одним RPC или ограниченным числом пакетных запросов.
- Миграции только добавляются в хронологическом порядке. Никогда не редактируй и не переименовывай уже применённую production-миграцию.
- Миграция должна быть воспроизводимой, по возможности идемпотентной, содержать grants/RLS/indexes для новых объектов и завершаться проверкой фактического поведения.
- Перед schema change сравни локальную и remote migration history; после изменения проверь список миграций и Supabase security/performance advisors.

### Текущее ограничение migration baseline

- Восстановленные baseline-миграции `20260809120330`, `20260809122317` и `20260809122825` входят в репозиторий. CI обязан успешно выполнить `supabase db reset --local`, pgTAP, database lint и diff сгенерированных TypeScript-типов.
- Production нельзя сбрасывать или переигрывать. Любая новая миграция additive и следует порядку: backup -> совместимая БД -> совместимый frontend -> enforcement.

## 10. Работа с пользовательскими данными

- Соблюдай принцип минимального раскрытия: публичному клиенту выдаются только данные, необходимые конкретному экрану.
- Email, auth identity, access token, административный признак и внутренние поля не должны попадать в публичную ленту, поиск, карточки, логи браузера или share-card.
- Всегда учитывай `users.is_public`, видимость родительской оценки и отношения дружбы.
- Пользователь может менять только собственные разрешённые поля профиля: `username`, `display_name`, `avatar_url`, `bio`, `is_public`. Избранные клубы изменяются отдельно через `set_favorite_club`; legacy `favorite_teams` не используется новыми интерфейсами.
- `ratings_count`, `avg_rating`, `streak`, `streak_date`, `invite_code` и `is_admin` являются серверно управляемыми данными; не вычисляй и не записывай их из формы профиля.
- Аватар перед выводом проходит URL-проверку. Editor нормализует изображение в JPEG, а файл хранится в owner-scoped bucket `avatars` с лимитом 2 MB и допустимыми MIME JPEG/PNG/WebP; в `users.avatar_url` хранится только HTTP(S)-URL.
- Вложения личных чатов хранятся только в приватном bucket `chat-media` по пути `<conversation_id>/<sender_id>/<safe_filename>`. Клиент получает временный signed URL; постоянный публичный URL не сохраняется.
- CSV-экспорты базы, лежащие вне репозитория, считай чувствительными production-like данными. Не копируй их в public assets, тестовые fixtures, Git или ответы пользователю.

## 11. Правила рейтингов и социальных действий

- Матч можно оценить только после статуса `finished`.
- Оценка матча и игрока — только целое число от 1 до 10.
- У пользователя может быть только одна оценка конкретного матча; повторное сохранение обновляет её атомарно.
- Перед сохранением пользователь обязан выбрать контекст оценки: болельщик хозяев, болельщик гостей или нейтральный зритель. Публичные агрегаты показывают общий и три сегментированных результата.
- Комментарий к оценке матча — максимум 1000 символов после trim.
- В одной операции разрешено максимум 60 player ratings; ID игроков должны быть уникальны и существовать.
- Лучший игрок может быть только один и обязан иметь пользовательскую оценку в том же payload.
- Player ratings принадлежат родительской паре `(user_id, match_id)` и удаляются вместе с основной оценкой.
- Счётчики профиля и streak обновляет база внутри rating transaction. Клиент только принимает возвращённый результат.
- Streak считается по уникальным UTC-дням создания оценок и остаётся активным только при оценке сегодня или вчера; редактирование старой оценки не продлевает серию.
- Свою оценку нельзя лайкать. Лайк возможен только для публичной оценки.
- Добавлять комментарии можно только к публичной оценке; удалять комментарий может только его автор.
- Feed scopes фиксированы: `all`, `friends`, `popular`, `mine`. Лента использует только keyset cursor из `get_social_feed_page`; не возвращай offset и не вычисляй `comment_count` по размеру загруженного фрагмента.
- Изменение оценки, реакции или комментария должно обновлять затронутый UI и не оставлять устаревшие счётчики/кэш.

## 12. Security requirements

- Никогда не коммить `.env`, API keys, service-role token, access token, реальные пароли или приватные CSV.
- Не ослабляй заголовки в `vercel.json`: CSP, HSTS, frame denial, referrer policy, permissions policy и `nosniff` являются обязательной частью production.
- При добавлении внешнего origin расширяй CSP только точным необходимым источником; не используй `*` и не ослабляй остальные directives.
- Не считай скрытую кнопку, клиентский route или `is_admin` в DOM средством защиты. Все привилегированные действия авторизуются на сервере или в БД.
- Не используй пользовательские metadata/JWT claims для ролей. Текущий административный признак хранится в защищённом `public.users.is_admin` и проверяется сервером.
- Не логируй токены, service key, email, тело пользовательского комментария или полный upstream payload.
- Фото, видео и голосовые сообщения чата считаются приватными пользовательскими данными: не публикуй bucket, не логируй signed URL и не выдавай файлы после прекращения дружбы.
- Любой новый ввод валидируй и в UI, и на доверенной границе: RPC, constraint или server function.
- Не вставляй непроверенные URL в `src`, `href`, CSS или canvas.
- `.vercelignore` обязан исключать `supabase/`, `tests/`, `scripts/`, `docs/`, `types/`, `README.md`, `AGENTS.md`, `tsconfig.json` и `.env.example` из публичной статики.
- Локальный E2E hook `window.__FOOTBAZED_TEST_CLIENT__` разрешён только на `localhost`/`127.0.0.1` при `?__e2e=1`.

## 13. UI/UX conventions

- Используй существующую дизайн-систему и CSS variables: `--bg*`, `--snow`, `--text*`, `--accent*`, `--b*`, semantic colors, `--r`, `--shadow`, `--ease`.
- Поддерживай `dark`, `light`, `system` и все четыре accents: `emerald`, `ice`, `gold`, `mono`. Новый компонент проверяется во всех темах; не хардкодь основной цвет вместо token.
- `Onest Variable` — основной self-hosted UI-шрифт; `Bebas Neue` — бренд, крупные числа и специальные display-заголовки. Не используй display-размеры в компактных панелях.
- Сохраняй спокойную футбольную эстетику: один пользовательский accent, нейтральные поверхности, чёткая иерархия и минимум визуального шума.
- Базовый radius карточек и контролов — около 8 px. Не создавай вложенные декоративные карточки без функциональной причины.
- Для повторяющихся элементов используй существующие классы кнопок, panels, empty/loading states и domain CSS вместо inline-style. Существующий inline CSS — legacy, не образец для нового кода.
- Каждый data screen обязан иметь loading, empty, error и retry states там, где повтор возможен.
- Деструктивные действия выполняются через `FBZConfirm`; не используй `window.confirm`.
- Диалоги открываются через `FBZOverlay`, чтобы сохранить focus trap, Escape, backdrop close и возврат фокуса.
- Icon-only button обязан иметь `aria-label` и обычно `title`. Toggle/tab/filter обязан синхронизировать `aria-pressed` или `aria-selected`.
- Сохраняй видимый `:focus-visible`, `aria-live` для асинхронных статусов и `prefers-reduced-motion` fallback.

## 14. Mobile requirements

- Mobile-first проверка обязательна, несмотря на desktop-ориентированную общую разметку.
- Основной responsive breakpoint — 900 px; дополнительные существующие границы доменов — 760/620/560/400/380 px. Не добавляй близкий случайный breakpoint без необходимости.
- Ни один экран не должен создавать горизонтальный scroll. Проверяй `document.documentElement.scrollWidth <= clientWidth + 1`.
- На ширине до 900 px учитывай fixed bottom navigation и сохраняй нижний page padding, чтобы она не перекрывала контент и действия.
- Таблицы, сетки, profile/entity/feed layouts должны переходить в одну колонку или контролируемый горизонтальный список, а не сжимать текст до нечитаемого состояния.
- Интерактивные элементы на мобильном должны иметь стабильный размер; критические touch targets, включая rating controls, ориентируются минимум на 42–44 px.
- Текст, team names, usernames и длинные комментарии не должны перекрывать соседние элементы; используй `min-width:0`, wrap, ellipsis или `overflow-wrap` по смыслу.
- Минимальный browser QA для пользовательского изменения: 390x844 и 1440x1000. Для компактных элементов дополнительно проверь ширину около 320–380 px.

## 15. Performance requirements

- Не загружай неограниченные коллекции. Используй pagination/load-more и жёсткие server limits.
- Независимые запросы выполняй через `Promise.all`; не делай последовательный waterfall без зависимости данных.
- Не добавляй N+1-запросы пользователей, лайков, комментариев или матчей. Используй aggregate RPC, joins или один пакетный `.in(...)` запрос.
- Используй существующий TTL cache только для некритичных публичных данных. После мутации вызывай соответствующую инвалидацию или обновляй UI из RPC result.
- Поиск и фильтры должны оставаться debounced; не отправляй запрос на каждую клавишу без задержки.
- Защищай UI от race conditions при смене маршрута, фильтра или запроса.
- Изображения вне первого viewport загружай лениво; не добавляй тяжёлые декоративные assets без WebP/разумного размера и визуальной проверки.
- Для новых SQL-paths проверяй indexes на foreign keys, WHERE, JOIN и ORDER BY, но не удаляй «unused» index только по статистике молодой/малонагруженной базы.
- Не увеличивай CSP surface и количество third-party runtime dependencies без необходимости.
- Сохраняй performance-бюджет главной: LCP не выше 2.5 s, CLS не выше 0.1 и стартовые JS/CSS не выше 500 KiB в локальном Playwright-контроле. Изменение бюджета требует измеренного обоснования.

## 16. Testing requirements

- Перед завершением любого изменения запускай минимум `pnpm run check`.
- Перед релизом, изменением маршрутов, Auth, Supabase-контрактов или основных сценариев запускай `pnpm run check:all`.
- `pnpm run check` обязан сохранять зелёными static checks и все `node:test` cases.
- Новую чистую доменную логику покрывай в `tests/domain.test.js`.
- Пользовательский сценарий, затрагивающий несколько экранов, Auth state, маршрутизацию или мобильную разметку, покрывай Playwright-тестом в `tests/e2e/`.
- E2E использует локальный deterministic Supabase mock и не должен читать или менять production.
- При расширении RPC-контракта обновляй mock только вместе с проверкой фактической формы production RPC.
- В E2E проверяй не только наличие текста, но и URL/title, доступные roles/labels, состояние действия и отсутствие `pageerror`.
- Для responsive-изменений добавляй или сохраняй проверку горизонтального overflow.
- Database change проверяется отдельными SQL-запросами/transaction tests: корректный happy path, запрет чужого доступа, anon behavior, ограничения и rollback тестовых данных.
- После DDL/RLS/function changes запускай Supabase security и performance advisors и разбирай новые WARN/ERROR до релиза.
- Не исправляй падающий тест ослаблением assertion, пока не доказано, что изменился согласованный продуктовый контракт.

## 17. Git и release workflow

- Перед изменениями проверяй `git status`. Не откатывай и не перезаписывай несвязанные пользовательские изменения.
- Коммиты должны быть небольшими и тематическими; сообщения — короткие, в повелительной форме, в стиле существующей истории (`Build ...`, `Align ...`, `Index ...`).
- Не коммить `node_modules`, `.env`, `.vercel`, `playwright-report`, `test-results`, debug logs и database CSV exports.
- Не используй `git reset --hard`, force-push или переписывание `main` без явного запроса владельца.
- Перед push: `git diff --check`, `pnpm run check:all`, проверка migration history и чистый `git status`.
- Новая клиентская функция, зависящая от schema/RPC, включается только после применения совместимой миграции.
- Breaking database contract разворачивай поэтапно: additive migration, совместимый client deploy, затем enforcement/cleanup migration.
- Массовая очистка данных разработки выполняется только через `api/admin.js`, серверный `service_role`, точную фразу подтверждения и RPC `admin_cleanup_development_data`; никогда не вызывай этот RPC из браузера.
- Production deploy считается завершённым только после push в `main`, HTTP-проверки Vercel и ручной/browser проверки изменённого пользовательского сценария.

## 18. Критические ограничения

- Не доверяй клиенту: весь клиентский JavaScript и anon key публичны.
- Не выполняй прямые client writes в `ratings`, `player_ratings`, `rating_likes` или `rating_comments`.
- Не выполняй прямые client writes в `chat_messages`, `direct_conversations` или `direct_messages`; не обходи проверку активной дружбы и RPC-лимиты сообщений.
- Не разрешай клиенту создавать/удалять notifications или менять в них что-либо кроме `read`.
- Не раскрывай `users.email`, `users.is_admin` или `users.invite_code` через общий public select; служебные счётчики выдавай только в уже разрешённом read-only наборе полей и никогда не разрешай клиенту их изменять.
- Футбольные изображения всегда optional. Используй только `FBZMedia` и связанные `media_assets` со статусом `verified`; не выводи deprecated `crest_url`/`photo_url`, `unknown`, `restricted` или `disabled` assets.
- Наличие URL у provider не подтверждает право использования. Новая интеграция media сначала документируется в `docs/sources/`, сохраняет provenance и остаётся выключенной до проверки конкретных прав.
- Не используй `live_chat_messages`, `support_tickets` и `referee_ratings` для новых функций: они не участвуют в текущих пользовательских сценариях и требуют отдельного решения по типам identity, grants и RLS.
- Сохраняй восстановленные baseline-миграции и проверяй, что чистая БД по-прежнему полностью разворачивается только из репозитория.
- Не обходи `api/admin.js` прямыми service-role запросами из браузера.
- Не ломай pretty deep links и обратную совместимость hash-ссылок, feature-loader, theme/accent contracts, mobile bottom navigation и E2E local-only guard.
- Локальная разработка, preview и CI не могут обращаться к production Supabase ref. Исключение `FOOTBAZED_ALLOW_PRODUCTION=1` допустимо только для явно контролируемой локальной диагностики и запрещено в CI.
- Не завершай работу без проверки безопасности данных, dark/light themes, desktop/mobile layout и автоматических тестов, соответствующих риску изменения.
