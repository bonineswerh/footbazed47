# FOOTBAZED: правила работы с проектом

Этот файл действует для всего репозитория. Он описывает фактическую архитектуру FOOTBAZED и обязательные правила для всех последующих изменений. Если архитектура проекта меняется, обновляй этот файл в том же изменении.

## 1. Назначение продукта

- FOOTBAZED — футбольная платформа с русским и английским интерфейсом, где болельщики оценивают завершённые матчи и игроков, ведут профиль, публикуют оценки, обсуждают матчи и взаимодействуют с друзьями.
- Основные публичные сущности: матчи, клубы, игроки, пользовательские профили и публичные оценки.
- Основные авторизованные сценарии: создание профиля, оценки матчей и игроков, прогнозы, друзья, сравнение вкусов, реакции и комментарии к рецензиям, уведомления.
- Администрирование встроено в основное приложение и доступно через `/admin`; `admin.html` существует только как `noindex`-редирект для старых ссылок.
- Продукт сейчас футбольный. Не обобщай доменную модель под другие виды спорта без отдельного архитектурного решения.

## 2. Подтверждённый стек

- Runtime-клиент — статическое SPA на HTML, CSS и обычном JavaScript без frontend-фреймворка, сборщика и компонентного runtime. TypeScript используется для сгенерированного контракта БД и CI-typecheck, но пока не исполняется в браузере.
- Навигация — History API с индексируемыми путями `/club/<id>`, `/player/<id>`, `/match/<id>`, `/profile/<uuid>` и статическими разделами. Старые hash-маршруты остаются только для обратной совместимости; маршрутизацией управляют `go`, `syncRoute` и `applyRouteFromLocation` в `app.js`.
- Данные, Auth и PostgreSQL — Supabase через `@supabase/supabase-js@2`.
- Серверная часть — CommonJS Vercel Functions: `api/config.js` для публичной runtime-конфигурации, `api/admin.js` для привилегированных действий и `api/sitemap.js` для динамического sitemap.
- Рабочий источник футбольного каталога — football-data.org через `api/admin.js`. API-Football используется для защищённой диагностики, staged подключения эмблем и preview/apply исторического состава точно сопоставленного матча. Массовый импорт матчей/игроков новым провайдером пока не включён.
- Production — Vercel из GitHub-ветки `main`.
- Тесты — встроенный `node:test`, pgTAP и Playwright Test с Axe. Требуется Node.js 22+.
- Менеджер зависимостей — pnpm: изменяя зависимости, обновляй и коммить `pnpm-lock.yaml`; не добавляй параллельный `package-lock.json`.

Не добавляй новый фреймворк, bundler, state manager, ORM или серверный слой только ради удобства отдельной функции. Такое изменение требует доказанной пользы для всего проекта и отдельного согласованного этапа миграции.

## 3. Карта ответственности файлов

Ожидания предстоящих матчей — отдельная оценка 1–10 с обязательным контекстом болельщика, без игроков и отзыва. `js/match-expectations.js` / `css/expectations.css` загружаются только на странице матча. Форма использует существующий lazy rating loader с mode=expectation. Значение 0 на шкале означает пустой черновик, никогда не сохраняется; 5 находится на 50%. `private.match_expectations` не имеет raw grants; writes выполняются owner-only RPC по auth.uid, до реального дедлайна и первого live/finished. Закрытие необратимо при регрессии статуса. Общий показатель включает публичные профили; сравнение до/после — только одинаковые пары автор+матч, не разность независимых средних. Старые predictions остаются в базе без преобразования. Сервер создаёт `match_ready` один раз при завершении ожидаемого матча, invoker `get_notifications_page_v2` обогащает прежний reader точной ссылкой. Нативные push-уведомления пока не реализованы.

`js/admin-guide.js` загружается по вкладке «Инструкция» без запросов к поставщику. Описывает реальные действия админки, предварительную проверку, применение/откат эмблем, границу модерации и резервную копию перед очисткой. Не добавляй объяснения несуществующих кнопок. Общие позиции поставщика Defence/Midfield/Offence сохраняются DF/MF/FW, без выдуманной точной роли.

- `index.html` — статическая оболочка страниц, навигация, доступные диалоги и порядок подключения клиентских скриптов.
- `styles.css` — дизайн-токены, общие компоненты, темы и основная адаптивность.
- `css/interaction-patterns.css` — единое оформление переключателей разделов, фильтров и ссылок на сущности. `FBZFeatures` загружает его один раз вместе с первым styled module и ждёт обе CSS до готовности; ошибка допускает retry даже при готовом script. Геометрия списков остаётся в domain CSS; selected/hover/focus используют общие tokens и не зависят от порядка lazy загрузки. На главной короткие правила club links остаются в shell CSS. Именная ссылка в ленте ограничена названием и эмблемой, а свободная поверхность открывает матч. Лайк — сердце и число, с доступным названием действия; подтверждённое состояние окрашивает оба элемента, не поверхность.
- Турнирная полоса главной использует две одинаковые группы шириной не меньше контейнера и ограниченный повтор названий; seam и пустые участки проверяются по фазам нескольких циклов. Hover не останавливает движение, отдельная кнопка допускает паузу. Reduced-motion показывает только исходные уникальные турниры. Карточки обзора сохраняют background/геометрию: подсветка — opacity отдельного слоя без pointer-events. Предстоящий матч использует внутри hero общие md-comm/md-segments для ожиданий; личное ожидание — md-own-rating ниже действий. Средние до игры не подменяют финальную оценку или paired сравнение.
- Годы матчевого календаря определяются через `FBZData.getMatchCalendarRange` с lazy `js/calendar-data.js`: два индексированных чтения только `match_date`, limit=1, до местного начала следующего года. Верхняя граница — текущий год; исторические годы появляются после реального импорта. Кэш 5 минут, timeout 8 секунд, route/session/request guards и retry. Ошибка или пустой каталог оставляют безопасный текущий год; просмотр календаря не вызывает провайдера. Ручной ввод, стрелки и клавиатура соблюдают те же границы. Асинхронный ответ сохраняет введённую дату и фокус.
- Переходы используют `--motion-fast` (120ms), `--motion-normal` (180ms), `--motion-slow` (260ms) и `--ease`; анимируй конкретные свойства, не размеры layout. Вход dialog/sheet и уведомлений лёгкий; reduced-motion отключает entry animation, delays и декоративные lifts. Окно «Настройки» хранит язык и локальное оформление, доступно гостю. Меню аккаунта содержит настройки, доступную администратору панель и выход. Профиль и друзья не дублируются в нём: профиль доступен в основной и мобильной навигации, друзья — в основной навигации и через счётчик собственного профиля на телефоне.
- `css/entities.css`, `css/feed.css`, `admin.css` — стили соответствующих доменов.
- `app.js` — иконки, общий shell, маршрутизация, настройки и совместимые глобальные оболочки ленивых модулей.
- `js/feature-loader.js` — единая загрузка JS/CSS модулей, таймауты и повтор после ошибки; готовность namespace не заменяет готовность CSS.
- `js/calendar-model.js` и `js/match-calendar.js` / `css/calendar.css` подключаются только в «Матчах». Первый модуль считает местные границы дня, включая переходы DST; второй владеет выбором даты, URL `m_day` / `m_favorites`, загрузкой календарного RPC и проверкой маршрута/сессии до и после optional media. `get_match_calendar_page` — invoker reader: фильтры применяются до count/limit, любимые клубы берутся только по auth.uid(); anon не получает raw grants на favorite_clubs. Старый `get_matches_page` остаётся для главной и всех дат без избранного. Не переносить эти модули в стартовую загрузку, не подменять серверный фильтр фильтрацией текущей страницы.
- `js/notification-counter.js` — лёгкий личный счётчик: RLS, обновление при фокусе и каждые 30 секунд только на видимой вкладке, 15 секунд при открытом центре. Head/count запрос отменяется после 8 секунд, при смене аккаунта, скрытии вкладки или подтверждённой мутации. Аккаунт передаётся явно через syncSession из renderNav; события focus/visibility безопасны до загрузки app, ответы предыдущего аккаунта отбрасываются. `js/notifications.js` и `css/notifications.css` загружаются при открытии центра. История использует invoker RPC и курсор `(created_at,id)`, отметка всех ограничена `through_id` снимка; новые события сохраняют unread. Ошибка обновления того же фильтра сохраняет загруженные строки, курсор, прокрутку и прежнюю границу. Изменившийся во время загрузки счётчик показывает предложение обновить список и сверяется после ответа. Поля событий клиент не создаёт и не меняет, кроме read. Оценки и точные комментарии открываются через bounded invoker readers с существующим scope ленты, без обхода первых 120 записей.
- `js/search.js` и `css/search.css` загружаются вместе только при явном открытии поиска. «Все» использует `search_footbazed_v2`: bounded invoker RPC обогащает старый ranked reader displayable media; fallback на старый RPC только при отсутствующей функции. Выбранная категория использует `search_footbazed_page`: category до limit, keyset `(relevance desc,title,id)`, bound query/kind cursor и одна страница до 24 результатов. Старые readers остаются совместимыми. Клиент группирует подборку по типу: порядок групп определяется первым совпадением, внутри сохраняется релевантность. Индексы клавиатуры совпадают с видимым порядком. Числа означают уже показанные результаты, не total каталога. Продолжение не меняет запрос/категорию; ошибка сохраняет предыдущую страницу и тот же cursor для retry. Отдельный status объявляет состояние без повторного чтения всего списка; очистка отменяет поздний ответ. Route/session и request guards, 180ms debounce и клавиатурные roles обязательны; изображения optional, без provider API или N+1.
- `js/actions.js` — делегирование DOM-событий через явный реестр функций; `js/shell-actions.js` — действия статической оболочки. Домен регистрирует собственные действия вместе с ленивым модулем. HTML передаёт только имя действия и экранированные JSON-параметры.
- Табло календаря, главного матча и ленты — настоящие ссылки с локализованным href. `FBZActions.follow` перехватывает только обычный click для SPA, сохраняя modifier-click и открытие в новой вкладке. CSS расширяет ссылку на свободную поверхность карточки; отдельные кнопки оценки/клуба находятся выше неё. Не добавляй transform на `:active` такой ссылки: он меняет containing block псевдоэлемента и срывает click по краю карточки. Скругления больших поверхностей используют `--radius-card`, компактных контролов — `--radius-control`; наведение не сдвигает раскладку.
- `css/typography.css` — общая шкала Onest, читаемые размеры, формы и адаптивные правила текста; подключается после основных стилей.
- `js/profile.js` и `css/profile.css` — ленивый профиль, фактическая статистика и дневник участия. `get_profile_page.rating_summary` агрегирует всю разрешённую историю независимо от bounded ratings page: владелец видит own, остальные public (включая accepted friends). Header/distribution/tournaments используют этот summary; старый RPC получает явно обозначенный sample fallback. Статус не должен выдавать количество оценок или лайков за экспертность.
- `js/comparison.js` и `css/comparison.css` — сравнение по явному нажатию «Сравнить» в видимом чужом профиле. Lazy dialog / mobile sheet, RLS invoker RPC, публичные finished-match оценки, отдельные exact / within-one / average gap, bounded pagination и интересы. Не вычисляет совместимость и не загружает сравнение при открытии профиля.
- `js/share.js` — ленивый экспорт профиля/оценки в PNG 1200×800 с загруженным кириллическим Onest.
- `js/core.js` — инициализация публичного Supabase-клиента из runtime-конфигурации, разрешённые наборы полей, кэш и функции безопасного вывода.
- `js/data.js` — единая клиентская граница агрегирующих и пагинированных RPC.
- `js/explore-model.js`, `js/explore.js` и `css/explore.css` — ленивые общие фильтры дневника и обзора: internal IDs, поиск вариантов, зависимые по actual fixtures клубы, URL и доступная modal/bottom sheet. `js/statistics.js` — ленивый `/discover`, старый `/leaderboard` совместим. Обзор учитывает только публичные оценки публичных профилей, показывает выборку и не ранжирует пользователей. Diary v2 использует курсор `(match_date,id)` и полные месячные summaries разрешённой отфильтрованной истории; старые клиенты сохраняют курсор `(created_at,id)`.
- `js/seo.js` — canonical, metadata и structured data для маршрутов.
- `api/page.js` — начальные HTML metadata публичных маршрутов, использующие тот же `js/seo.js`; только publishable key, минимальные поля, без cookies/tokens посетителя. Это не полный SSR. Шаблон `dist/index.html` включается в Vercel Function через `includeFiles`.
- `js/session-hint.js` и `js/performance.js` — безопасная ранняя стабилизация layout и локальная диагностика LCP/CLS/длительности взаимодействий без пользовательских данных и сетевой отправки. Это не RUM и не сертифицированный расчёт INP.
- `js/domain.js` — чистая доменная логика, доступная и браузеру, и `node:test`.
- Обзор и дневник фиксируют страницу/курсор только после успешного чтения. При временном сбое в той же выборке сохраняют подтверждённые результаты и повторяют тот же запрос; смена фильтров, отказ доступа, отмена и недоступный профиль очищают данные. Успешный переход страницы возвращает фокус к заголовку списка, если пользователь не перешёл к другому контролу или диалогу.
- `js/auth.js`, `js/ratings.js`, `js/matches.js`, `js/entities.js`, `js/feed.js`, `js/search.js`, `js/admin.js` — владельцы своих доменов. `js/rating-loader.js` сохраняет глобальную оболочку `openRate()` и лениво подключает `js/ratings.js` вместе с `css/ratings.css`, затем вызывает `FBZRatings.open()`. Реализация не заменяет оболочку: повтор после ошибки CSS обязан снова проходить через loader. Не возвращай эти модули в критический путь главной страницы.
- `js/appearance.js`, `js/overlays.js`, `js/confirm.js`, `js/account.js` — общие UI-механизмы.
- `js/community-reports.js` и `css/community-reports.css` загружаются только по запросу: жалоба на публично доступную чужую запись, комментарий или профиль и собственная история по 10 обращений. Диалог использует общий overlay и отменяет поздние результаты при смене маршрута/сессии. Административная очередь по 20 строк загружается отдельно во вкладке «Жалобы».
- `api/admin.js` и `api/sitemap.js` — доверенные серверные границы с `service_role`; ключ никогда не передаётся клиенту.
- `server/football/api-football.js` — CommonJS provider client без собственного HTTP endpoint: fixed origin/allowlist, bounded timeout/body/pagination/request budget, quota reserve и безопасные ошибки. `API_FOOTBALL_KEY` используется только на сервере. GET overview сообщает лишь configured; реальный API вызывается только отдельной admin-командой. Unit/E2E не расходуют настоящую квоту. `server/football/match-lineups.js` сопоставляет fixture по обоим provider team IDs, турниру, сезону и времени; максимум четыре запроса, честный plan/coverage fallback.
- `supabase/migrations/` — полная последовательная история production-схемы, воспроизводимая на пустой локальной БД.
- `types/database.ts` — генерируемый Supabase-контракт. Не редактируй вручную; CI сравнивает его с чистой БД после всех миграций.
- `tests/domain.test.js` — unit-тесты чистой логики.
- `tests/e2e/` — детерминированные авторизованные браузерные сценарии без записи в production.

## 4. Архитектурные правила

- Не раздувай `app.js` новой крупной доменной логикой. Новые самостоятельные функции размещай в отдельном `js/<domain>.js` и экспортируй одним пространством имён `window.FBZ<Domain>`.
- Новые клиентские доменные модули оформляй как IIFE с `'use strict'`, закрытым состоянием и минимальным публичным API. Существующие глобальные функции сохраняются для совместимости доменов. Inline-обработчики запрещены; используй addEventListener или FBZActions.register/attrs.
- Чистые правила валидации, сортировки и нормализации размещай в `js/domain.js`, чтобы их можно было тестировать без DOM и Supabase.
- Порядок стартовых `<script>` в `index.html` является контрактом зависимостей. `domain.js`, appearance/core и общие UI-модули должны быть загружены до кода, который их вызывает. `feed`, `entities` и `admin` загружаются только через `ensureFeatureModule`; не возвращай их в стартовый HTML.
- Для изменённого CSS или клиентского JS обновляй query-версию соответствующего `src`/`href` в `index.html`, чтобы Vercel и браузеры не оставляли устаревший asset.
- Не создавай вторую систему маршрутизации. Новые ссылки используют красивые пути без hash; парсинг старых hash-ссылок сохраняется до отдельной совместимой миграции.
- Не создавай отдельную админку или отдельную модель авторизации: административный интерфейс остаётся страницей основного SPA, а реальная авторизация выполняется сервером.

## 5. Frontend conventions

- Интерфейс поддерживает русский и английский языки; бренд всегда отображается как `FOOTBAZED`. Русские маршруты сохраняются, английские используют префикс `/en`. Единственный роутер в `app.js` обрабатывает обе версии через `FBZLocale`.
- `locales/en.json` содержит переводы авторских UI-строк. `scripts/localization.mjs` при сборке создаёт английскую оболочку и скрипты: не переводятся пользовательские тексты, provider-данные, wire constants и ключи. Пропущенный перевод останавливает сборку. Runtime-наблюдатели DOM, eval и скачивание всего словаря в браузер не допускаются.
- Названия клубов и турниров выводятся через `FBZNames`: короткая подпись в карточках, полная на странице клуба. ID и исходные provider-имена не меняются. Поиск использует `club_aliases` до limit/pagination, а не переводит ограниченную клиентскую выдачу.
- При создании HTML из строк экранируй каждый пользовательский и внешний текст через `esc()`.
- Для действий в строковых HTML-шаблонах используй `FBZActions.attrs(name, args, event)`: параметры сериализуются в JSON и экранируются. Не вставляй исполняемые строки в HTML, не добавляй eval/Function и не разрешай вызов произвольного глобального имени. Делегированный submit читает форму через event.target, а не event.currentTarget (это document).
- Внешние и пользовательские изображения пропускай через `safeImageUrl()`. Для `<img>` используй подходящие `alt`, `loading` и `decoding`.
- Для простого текста предпочитай `textContent`; `innerHTML` допустим только для контролируемого шаблона с экранированными значениями.
- Не показывай пользователю необработанные сообщения Supabase, Auth, PostgreSQL или внешнего API. Локализуй ожидаемые ошибки и выводи безопасный fallback.
- У любой async-команды должны быть состояния loading/disabled, обработка ошибки и восстановление кнопки в `finally`.
- Для запросов, результат которых может устареть, применяй версию запроса или другой механизм отмены, как в поиске, ленте и страницах сущностей.
- Используй существующие `FBZOverlay`, `FBZConfirm`, `toast`, `ico`, `copyText`, `getCache`/`setCache`; не создавай параллельные реализации модалок, подтверждений, уведомлений или кэша.
- Новые иконки добавляй в существующий реестр `I` и получай через `ico()`. Не размножай произвольные inline SVG по шаблонам.
- Не сохраняй access token, пароль, email или другие чувствительные данные в пользовательские ключи `localStorage`. Текущий local storage предназначен для внешнего вида, недавних запросов и некритичного кэша `fb_*`.

## 6. Backend conventions

- `api/admin.js` остаётся CommonJS Vercel Function и возвращает JSON с `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.
- Каждый административный запрос обязан передавать Supabase access token в `Authorization: Bearer ...`.
- Сервер обязан самостоятельно проверить token через Supabase Auth и затем проверить `users.is_admin`. Проверка `CU.is_admin` на клиенте — только UX, не авторизация.
- После проверки подписи Auth сервер привязывает JWT к пользователю, issuer, audience, expiry и session_id. Service-only `admin_auth_session_state` проверяет живую Auth session, защищённый флаг администратора и действующий TOTP factor. Все административные данные/операции требуют JWT и session AAL2; очистка дополнительно требует TOTP amr не старше пяти минут. AAL1 допускает только собственный access_status, без каталога/жалоб/поставщика. Не добавлять MFA bypass. `js/admin-security.js` загружается только в админке, использует SDK MFA и общие overlays; QR/ключ/код не попадают в storage/logs, очищаются при закрытии, выходе и смене маршрута. Код и настоящий QR вводит/сканирует владелец сам. Заблокированная очистка никогда не повторяется автоматически.
- QR от Auth может быть большим pixel SVG: поддерживай ограниченный data URI только в `img`, включая raw, percent-encoded и base64. При ошибке изображения оставляй ручное подключение того же фактора; не создавай и не удаляй TOTP автоматически. Проверяй совместимость с настоящим bundled SDK на искусственном SVG и credentials, без запросов к production Auth.
- `SUPABASE_SERVICE_ROLE_KEY` используется только на сервере и только после успешной проверки администратора.
- Все действия API должны находиться в явном allowlist, проверять method, типы, диапазоны, даты и перечисления. Сохраняй ограничение тела запроса и timeout внешнего API.
- Ошибки 500 не должны раскрывать детали базы, ключи, SQL или upstream response. Подробности допустимы только в server log.
- football-data.org вызывается только сервером. Не передавай `FOOTBALL_DATA_API_KEY` в клиент и не вызывай внешний API напрямую из браузера.
- Синхронизация должна быть идемпотентной: внешние сущности связываются по `external_id`, игроки — по существующему уникальному контракту, upsert не должен создавать дубликаты.
- Existing `external_id` относится к football-data.org; не записывай туда API-Football IDs. До нового импорта нужны FK provider mappings, collision review и совместимый historical roster contract. Legacy prepared-catalog apply очищает данные и не подходит для перехода провайдера. План: `docs/api-football-transition-2026-09-30.md`.

## 7. Supabase и Data API

- Публичный anon/publishable key допустим в клиенте; secret/service-role key — никогда.
- RLS и SQL grants — независимые уровни. Для доступной через Data API таблицы должны быть одновременно настроены необходимые grants и корректные RLS policies.
- Используй минимальные grants. Для `users` сохраняй column-level доступ: публично читаются только поля из `PUBLIC_USER_FIELDS`; `email`, `invite_code` и `is_admin` не раскрываются, а агрегаты `ratings_count`, `avg_rating`, `streak`, `streak_date` доступны для чтения, но не для клиентской записи.
- Собственный полный профиль загружается через `get_my_profile`; email берётся из Supabase Auth session, а не из публичного `users`-select.
- Клиент может обновлять в `notifications` только колонку `read`. Создание уведомлений выполняют серверные triggers/functions.
- Оценки матчей и игроков изменяются только через `save_match_rating` и `delete_match_rating`.
- Messaging выведен из первой версии. Не возвращай его UI, RPC grants, Storage доступ или realtime; архивные таблицы и функции сохраняются без клиентского доступа.
- Лайки и комментарии оценок изменяются только через `toggle_rating_like`, `add_rating_comment` и `delete_rating_comment`.
- `community_reports` читается пользователем только для собственных строк и разрешённых колонок; snapshot, отправитель, автор и проверяющий не выдаются этим select. Создание только через `submit_community_report`, auth.uid() определяет отправителя. Повтор открытой жалобы идемпотентен; лимиты — 5 за 10 минут и 20 за сутки.
- `admin_get_community_reports` и `admin_review_community_report` доступны только service_role: API выводит actor из проверенной сессии, SQL повторно проверяет защищённый users.is_admin. Закрытие жалобы и append-only audit атомарны. Текущий triage не скрывает контент, не удаляет оценки и не блокирует аккаунты автоматически.
- Общие футбольные показатели используют закрытые `private.community_public_match_votes` / `private.community_public_player_votes`: только публичные parent ratings, без client grants на исходные строки. Четыре aggregate-only RPC (`get_club_page`, `get_player_page`, `get_match_insights`, `get_football_statistics`) имеют fixed-path SECURITY DEFINER для одинакового результата при личных RLS-фильтрах. Они не возвращают voter IDs или reviews; favorite flag всегда ограничен auth.uid(). Own history и остальные readers сохраняют свои RLS/privacy scopes. Overview дополнительно исключает закрытые профили; существующий match insight scope публичных votes не расширяется.
- Личные блокировки хранятся в закрытой private.community_user_blocks без client table grants. Только set_user_block/get_my_user_blocks выводят actor из auth.uid(); собственный bounded список содержит ранее видимые labels, но не входящие блокировки. Restrictive SELECT policies и explicit definer reader guards обеспечивают взаимную видимость для signed-in users; anonymous public scope сохраняется. Positive contact writes сериализуются тем же pair advisory lock, что блокировка и friendship RPC; удаление собственных реакций/комментариев и снятие блокировки остаются доступны. Исторические данные не удаляются. После мутации lazy community-blocks invalidates pending reads/caches, очищает personal UI и уведомления и переводит на главную; не эмулирует logout.
- Не возвращай в RPC лишние колонки. Публичные агрегаты должны отдавать минимальный готовый payload, как `get_social_feed_page`, `get_club_page`, `get_player_page` и `get_match_insights`.
- Для независимых публичных чтений предпочитай `SECURITY INVOKER`. `SECURITY DEFINER` допустим только для подтверждённой серверной операции или безопасного агрегата, которому нужен контролируемый обход RLS.
- Любая `SECURITY DEFINER` function обязана иметь `set search_path = ''`, schema-qualified объекты, проверку `auth.uid()`/владения для мутаций, строгую валидацию и явные `REVOKE`/`GRANT EXECUTE`.
- Trigger-functions не должны быть напрямую доступны `anon` или `authenticated`.
- После изменения функций или grants выполняй `notify pgrst, 'reload schema'`, если PostgREST должен перечитать контракт.

## 8. Правила RLS

- RLS обязателен для каждой таблицы в exposed schema `public`, включая новые таблицы.
- Не используй `TO authenticated` как достаточную авторизацию. Политика должна ограничивать строки по `auth.uid()`, владельцу, адресату, публичности или подтверждённой дружбе.
- Для UPDATE всегда задавай и `USING`, и `WITH CHECK`, чтобы владелец не мог перепривязать запись другому пользователю.
- Для INSERT пользовательский идентификатор должен совпадать с `(select auth.uid())`; не доверяй `user_id` из браузера без policy/function проверки.
- Публичная оценка доступна всем, приватная — только её автору. Player ratings, likes и comments должны наследовать видимость родительской оценки.
- Профиль видим, если он публичный, принадлежит текущему пользователю или доступен подтверждённому другу. Не обходи `is_user_visible` прямым широким users-select.
- Дружба двусторонняя по чтению, но запрос создаёт отправитель, а pending-запрос принимает или отклоняет только адресат.
- Архив чатов недоступен anon/authenticated даже участникам беседы; restrictive RLS не позволяет открыть его случайным grant.
- Уведомления читает и помечает прочитанными только их получатель.
- Проверяй политики минимум как `anon`, пользователь-владелец и другой `authenticated` пользователь. Проверка только под `service_role` ничего не доказывает, потому что он обходит RLS.

## 9. Database conventions

- SQL-имена — `snake_case`; таблицы во множественном числе; foreign keys заканчиваются на `_id`; внешние провайдерские IDs хранятся отдельно как `external_id`.
- Пользовательская identity — UUID из `auth.users`. Футбольные сущности используют существующие bigint identity IDs.
- Новые даты событий храни в `timestamptz`, если нет доказанной причины для другого типа.
- Инварианты закрепляй на уровне БД через `NOT NULL`, `CHECK`, `UNIQUE` и foreign keys, а не только через форму.
- Для удаления выбирай осознанную семантику: зависимые пользовательские детали оценки удаляются cascade; исторические ссылки на клуб допускают `SET NULL`.
- Индексируй foreign keys и реальные пути поиска/фильтрации/сортировки. Для частых подмножеств предпочитай частичные индексы, как уникальные best-player и notification indexes.
- Любой потенциально многозаписный ответ должен иметь серверный limit. Лента использует cursor pagination; матчи временно используют bounded offset pagination через `get_matches_page`.
- Не создавай N+1-запросы ради карточек. Сложные страницы и лента должны получать агрегированный payload одним RPC или ограниченным числом пакетных запросов.
- Миграции только добавляются в хронологическом порядке. Никогда не редактируй и не переименовывай уже применённую production-миграцию.
- Миграция должна быть воспроизводимой, по возможности идемпотентной, содержать grants/RLS/indexes для новых объектов и завершаться проверкой фактического поведения.
- Перед schema change сравни локальную и remote migration history; после изменения проверь список миграций и Supabase security/performance advisors.

### Текущее ограничение migration baseline

- Восстановленные baseline-миграции `20260809120330`, `20260809122317` и `20260809122825` входят в репозиторий. CI обязан успешно выполнить `supabase db reset --local`, pgTAP, database lint и diff сгенерированных TypeScript-типов.
- Production нельзя сбрасывать или переигрывать. Любая новая миграция additive и следует порядку: backup -> совместимая БД -> совместимый frontend -> enforcement.

## 10. Работа с пользовательскими данными

- Соблюдай принцип минимального раскрытия: публичному клиенту выдаются только данные, необходимые конкретному экрану.
- Email, auth identity, access token, административный признак и внутренние поля не должны попадать в публичную ленту, поиск, карточки, логи браузера или share-card.
- Всегда учитывай `users.is_public`, видимость родительской оценки и отношения дружбы.
- Пользователь может менять только собственные разрешённые поля профиля: `username`, `display_name`, `avatar_url`, `bio`, `is_public`. Избранные клубы изменяются отдельно через `set_favorite_club`; legacy `favorite_teams` не используется новыми интерфейсами.
- `ratings_count`, `avg_rating`, `streak`, `streak_date`, `invite_code` и `is_admin` являются серверно управляемыми данными; не вычисляй и не записывай их из формы профиля.
- Аватар перед выводом проходит URL-проверку. Editor нормализует изображение в JPEG, а файл хранится в owner-scoped bucket `avatars` с лимитом 2 MB и допустимыми MIME JPEG/PNG/WebP; в `users.avatar_url` хранится только HTTP(S)-URL.
- Приватный bucket `chat-media` хранит архив без клиентского доступа. Не удаляй архив и объекты без отдельного решения владельца и backup.
- CSV-экспорты базы, лежащие вне репозитория, считай чувствительными production-like данными. Не копируй их в public assets, тестовые fixtures, Git или ответы пользователю.

## 11. Правила рейтингов и социальных действий

- Матч можно оценить только после статуса `finished`.
- Оценка матча и игрока — только целое число от 1 до 10.
- У пользователя может быть только одна оценка конкретного матча; повторное сохранение обновляет её атомарно.
- Перед сохранением пользователь обязан выбрать контекст оценки: болельщик хозяев, болельщик гостей или нейтральный зритель. Публичные агрегаты показывают общий и три сегментированных результата.
- Комментарий к оценке матча — максимум 1000 символов после trim.
- В одной операции разрешено максимум 60 player ratings; ID игроков должны быть уникальны и существовать.
- Лучший игрок может быть только один и обязан иметь пользовательскую оценку в том же payload.
- Player ratings принадлежат родительской паре `(user_id, match_id)` и удаляются вместе с основной оценкой.
- Новые player ratings требуют подтверждённого исторического участия: starter либо вышедший substitute в `match_player_appearances`. Текущий squad клуба не доказывает участие. Provider mappings и import batches service-only, snapshot клуба исторический. Старые неподтверждённые оценки можно сохранить без изменения или явно удалить; заново создать или повысить их нельзя. Не угадывай identities по имени.
- Историческая принадлежность выступления берётся только из подтверждённого appearance. Закрытый `private.community_player_performances` нормализует прежний публичный aggregate scope; raw grants отсутствуют. Legacy получает null клуба, без fallback на текущий players.club_id. Club/player averages и выбор лучшего игрока считают подтверждённые выступления; прежние оценки остаются отдельно в истории. `get_club_page.rated_performers` показывает и ушедших игроков, тогда как squad остаётся текущим. Overview игроков по умолчанию передаёт `confirmed_only:true`; отдельный режим всей истории сохраняет legacy, но не ранжирует неподтверждённую выборку. Клубный фильтр игроков означает сторону выступления, а матчевый — любую участвующую команду.
- Счётчики профиля и streak обновляет база внутри rating transaction. Клиент только принимает возвращённый результат.
- Streak считается по уникальным UTC-дням создания оценок и остаётся активным только при оценке сегодня или вчера; редактирование старой оценки не продлевает серию.
- Свою оценку нельзя лайкать. Лайк возможен только для публичной оценки.
- Добавлять комментарии можно только к публичной оценке; удалять комментарий может только его автор.
- Feed scopes: `all`, `experts`, `friends`, `mine`; legacy `popular` остаётся совместимым серверным контрактом. Эксперты назначаются только через защищённый admin API, private.community_experts не имеет client grants. Лента использует только keyset cursor из `get_social_feed_page`; не возвращай offset и не вычисляй `comment_count` по размеру загруженного фрагмента.
- Изменение оценки, реакции или комментария должно обновлять затронутый UI и не оставлять устаревшие счётчики/кэш.

## 12. Security requirements

- Никогда не коммить `.env`, API keys, service-role token, access token, реальные пароли или приватные CSV.
- Не ослабляй заголовки в `vercel.json`: CSP, HSTS, frame denial, referrer policy, permissions policy и `nosniff` являются обязательной частью production.
- CSP для JavaScript: `script-src 'self'; script-src-attr 'none'`. Не возвращай unsafe-inline/unsafe-eval для скриптов. Стили пока допускают unsafe-inline для существующих CSS-переменных и вычисляемых размеров; это отдельный контракт. Локальный HTTP-loopback сервер сохраняет ограничения скриптов, исключая только transport directives HSTS и upgrade-insecure-requests. Production сохраняет оба.
- При добавлении внешнего origin расширяй CSP только точным необходимым источником; не используй `*` и не ослабляй остальные directives.
- Не считай скрытую кнопку, клиентский route или `is_admin` в DOM средством защиты. Все привилегированные действия авторизуются на сервере или в БД.
- Не используй пользовательские metadata/JWT claims для ролей. Текущий административный признак хранится в защищённом `public.users.is_admin` и проверяется сервером.
- Не логируй токены, service key, email, тело пользовательского комментария или полный upstream payload.
- Микрофон запрещён Permissions Policy, media-src содержит none; realtime origin не нужен продукту.
- Любой новый ввод валидируй и в UI, и на доверенной границе: RPC, constraint или server function.
- Персональная очистка уведомлений хранится отдельно в `notification_dismissals`; `set_notification_dismissed` работает как invoker, допускает только свои доступные события и обратную отмену. Restrictive SELECT policy исключает очищенные события до pagination и из всех unread counts. Её private definer predicate читает только own dismissal metadata, разрывая рекурсию с INSERT policy; события и их privacy scopes не обходит. Raw notifications DELETE/INSERT и identity updates остаются закрыты; очистка не отвечает на заявку в друзья и не меняет read state.
- Не вставляй непроверенные URL в `src`, `href`, CSS или canvas.
- `.vercelignore` обязан исключать `supabase/`, `tests/`, `scripts/`, `docs/`, `types/`, `README.md`, `AGENTS.md`, `tsconfig.json` и `.env.example` из публичной статики.
- Локальный E2E hook `window.__FOOTBAZED_TEST_CLIENT__` разрешён только на `localhost`/`127.0.0.1` при `?__e2e=1`.

## 13. UI/UX conventions

- Календарь дат в `js/match-calendar.js` использует общий overlay, локальную месячную сетку и roving focus (стрелки, Home/End, PageUp/PageDown). Просмотр месяца не вызывает RPC; выбор даты сохраняет избранное и прежние серверные фильтры. Переход маршрута/сессии закрывает панель. Profile editor сохраняет заголовок и действия вне прокручиваемого тела формы.
- Ожидание — предполагаемое качество игры, не интерес к просмотру. Среднее ожидание и итоговая оценка показаны раздельно; сравнение до/после относится только к тем же авторам. Разницы личной оценки и средней общества в интерфейсе матча нет. Геометрия всех rating rails учитывает реальный thumb 28 px; 0 — пустой черновик, midpoint 5 — 50%, цифры — одна строка из 11 делений. Матч и ожидание используют один ползунок, число и смысловую подпись без дублирующего select; у игрока сохраняется отдельный числовой select. Общие lazy `js/form-controls.js` / `css/form-controls.css` подменяют OS-popup при взаимодействии с select/date, сохраняя native value, FormData и validation. Панель внутри активного overlay не открывает вторую модалку; Escape закрывает выбор до родительского диалога. Клубные и турнирные фильтры обзора/дневника ищут внутри списка по обоим языкам; видимые эмблемы получают существующим bounded reader и показывают только через `FBZMedia`.

- При изменениях поиска и отображения клубов, игроков и оценок сверяй сценарий с актуальными Sofascore, FotMob и Flashscore. Записывай наблюдение и собственный вывод; сохраняй стилистику FOOTBAZED. Оценки болельщиков не подменяются статистическим рейтингом провайдера. Фильтр категории должен применяться на сервере до limit/pagination; не выдавай фильтрацию ограниченной подборки за поиск по всему каталогу.
- Используй существующую дизайн-систему и CSS variables: `--bg*`, `--snow`, `--text*`, `--accent*`, `--b*`, semantic colors, `--r`, `--shadow`, `--ease`.
- Поддерживай `dark`, `light`, `system` и все четыре accents: `emerald`, `ice`, `gold`, `mono`. Новый компонент проверяется во всех темах; не хардкодь основной цвет вместо token.
- `Onest Variable` — основной self-hosted UI-шрифт, включая оценки, счёт и числовые показатели. Общая numeric hierarchy в `css/typography.css` задаёт tabular/lining цифры и насыщенность 650; новые lazy CSS не должны её отменять. `Bebas Neue` сохраняется для бренда и специальных display-элементов. Не используй display-размеры в компактных панелях.
- Сохраняй спокойную футбольную эстетику: один пользовательский accent, нейтральные поверхности, чёткая иерархия и минимум визуального шума.
- Цвет оценки определяет только `FBZDomain.ratingTone`: 1–3 красный, выше 3 и ниже 7 янтарный, 7–8.9 зелёный, 9–10 голубой. Средние оценки используют тот же контракт; тема меняет контраст, но не смысл цвета.
- Матчевые поверхности используют `FBZDomain.matchPaletteStyle` и `css/club-palettes.css`: мягкий цвет хозяев слева, гостей справа. Неизвестные клубы нейтральны; произвольные строки цветов из внешнего API не вставляются в CSS.
- Большие поверхности используют `--radius-card` (20 px), компактные контролы — `--radius-control` (12 px); существующие служебные кнопки сохраняют контракт 8 px. Не создавай вложенные декоративные карточки без функциональной причины.
- Для повторяющихся элементов используй существующие классы кнопок, panels, empty/loading states и domain CSS вместо inline-style. Существующий inline CSS — legacy, не образец для нового кода.
- Каждый data screen обязан иметь loading, empty, error и retry states там, где повтор возможен.
- Деструктивные действия выполняются через `FBZConfirm`; не используй `window.confirm`.
- Диалоги открываются через `FBZOverlay`, чтобы сохранить focus trap, Escape, backdrop close и возврат фокуса. Общий механизм временно изолирует фон через inert и aria-hidden, сохраняя исходные значения; перенос фокуса выполняется до скрытия прежнего предка. Не ставь inert на предка активного диалога, в том числе у вложенных и вынесенных из формы панелей.
- Icon-only button обязан иметь `aria-label` и обычно `title`. Toggle/tab/filter обязан синхронизировать `aria-pressed` или `aria-selected`.
- Сохраняй видимый `:focus-visible`, `aria-live` для асинхронных статусов и `prefers-reduced-motion` fallback.

## 14. Mobile requirements

- Mobile-first проверка обязательна, несмотря на desktop-ориентированную общую разметку.
- Основной responsive breakpoint — 900 px; дополнительные существующие границы доменов — 760/620/560/400/380 px. Не добавляй близкий случайный breakpoint без необходимости.
- Ни один экран не должен создавать горизонтальный scroll. Проверяй `document.documentElement.scrollWidth <= clientWidth + 1`.
- На ширине до 900 px учитывай fixed bottom navigation и сохраняй нижний page padding, чтобы она не перекрывала контент и действия.
- Таблицы, сетки, profile/entity/feed layouts должны переходить в одну колонку или контролируемый горизонтальный список, а не сжимать текст до нечитаемого состояния.
- Интерактивные элементы на мобильном должны иметь стабильный размер; критические touch targets, включая rating controls, ориентируются минимум на 42–44 px.
- Текст, team names, usernames и длинные комментарии не должны перекрывать соседние элементы; используй `min-width:0`, wrap, ellipsis или `overflow-wrap` по смыслу.
- Минимальный browser QA для пользовательского изменения: 390x844 и 1440x1000. Для компактных элементов дополнительно проверь ширину около 320–380 px.

## 15. Performance requirements

- Не загружай неограниченные коллекции. Используй pagination/load-more и жёсткие server limits.
- Независимые запросы выполняй через `Promise.all`; не делай последовательный waterfall без зависимости данных.
- Не добавляй N+1-запросы пользователей, лайков, комментариев или матчей. Используй aggregate RPC, joins или один пакетный `.in(...)` запрос.
- Используй существующий TTL cache только для некритичных публичных данных. После мутации вызывай соответствующую инвалидацию или обновляй UI из RPC result.
- Поиск и фильтры должны оставаться debounced; не отправляй запрос на каждую клавишу без задержки.
- Защищай UI от race conditions при смене маршрута, фильтра или запроса.
- Изображения вне первого viewport загружай лениво; не добавляй тяжёлые декоративные assets без WebP/разумного размера и визуальной проверки.
- Для новых SQL-paths проверяй indexes на foreign keys, WHERE, JOIN и ORDER BY, но не удаляй «unused» index только по статистике молодой/малонагруженной базы.
- Не увеличивай CSP surface и количество third-party runtime dependencies без необходимости.
- Сохраняй performance-бюджет главной: LCP не выше 2.5 s, CLS не выше 0.1 и стартовые JS/CSS не выше 500 KiB в локальном Playwright-контроле. Изменение бюджета требует измеренного обоснования.

## 16. Testing requirements

- Перед завершением любого изменения запускай минимум `pnpm run check`.
- Перед релизом, изменением маршрутов, Auth, Supabase-контрактов или основных сценариев запускай `pnpm run check:all`.
- `pnpm run check` обязан сохранять зелёными static checks и все `node:test` cases.
- Новую чистую доменную логику покрывай в `tests/domain.test.js`.
- Пользовательский сценарий, затрагивающий несколько экранов, Auth state, маршрутизацию или мобильную разметку, покрывай Playwright-тестом в `tests/e2e/`.
- E2E использует локальный deterministic Supabase mock и не должен читать или менять production.
- При расширении RPC-контракта обновляй mock только вместе с проверкой фактической формы production RPC.
- В E2E проверяй не только наличие текста, но и URL/title, доступные roles/labels, состояние действия и отсутствие `pageerror`.
- Для responsive-изменений добавляй или сохраняй проверку горизонтального overflow.
- Database change проверяется отдельными SQL-запросами/transaction tests: корректный happy path, запрет чужого доступа, anon behavior, ограничения и rollback тестовых данных.
- После DDL/RLS/function changes запускай Supabase security и performance advisors и разбирай новые WARN/ERROR до релиза.
- Не исправляй падающий тест ослаблением assertion, пока не доказано, что изменился согласованный продуктовый контракт.

## 17. Git и release workflow

- main защищена активным ruleset FOOTBAZED main quality gate (24746363): PR, актуальная относительно main ветка и три required checks с источником GitHub Actions; удаления/force push запрещены, bypass list пуст. Required approvals=0 для одного владельца. Работать в feature/**, открывать PR и сливать после CI, затем проверять отдельный main-push CI и Production. Не обходить правила прямым push или отключением ruleset.
- Production-сборка в `scripts/build-static.mjs` вызывает `scripts/check-release.mjs` до записи bundle: требуется успешный push-run `.github/workflows/ci.yml` именно для `VERCEL_GIT_COMMIT_SHA` ветки main и три успешные jobs application/database/secrets. Preview/local не ждут CI. Нет bypass-переменной: отказ/таймаут 25 минут останавливает публикацию. `/release.json` содержит только verified, commit и qualityRunId; ручной upload без Git identity не публикуется этим build path. Изменяемость build command/ветки владельцем остаётся отдельной границей, это не замена защиты main.
- Приватный GitHub требует сохранения main enforcement на подходящем плане и проверенного доступа Vercel к Actions. Необязательный `FOOTBAZED_GITHUB_READ_TOKEN` используется только production build для фиксированных GitHub API reads с redirect:error, не выводится и не публикуется. Нужен fine-grained Actions Read-only только footbazed47; credential создаёт и вводит владелец. Смена visibility — после успешной контрольной сборки с токеном, не обход gate. Порядок описан в `docs/private-repository.md`.
- `scripts/check-production.mjs` читает только публичные RU/EN shell, release.json, стартовый JS/CSS и проверяет отказ guest admin. Workflow Production availability выполняет его каждые 30 минут по расписанию GitHub (возможны задержки). Не читать ключи, provider payload, отзывы или сессии ради мониторинга; ошибка содержит только безопасный код. Это проверка доступности, не RUM/сборщик runtime errors и не контроль актуальности каталога.
- Перед изменениями проверяй `git status`. Не откатывай и не перезаписывай несвязанные пользовательские изменения.
- Коммиты должны быть небольшими и тематическими; сообщения — короткие, в повелительной форме, в стиле существующей истории (`Build ...`, `Align ...`, `Index ...`).
- Не коммить `node_modules`, `.env`, `.vercel`, `playwright-report`, `test-results`, debug logs и database CSV exports.
- Не используй `git reset --hard`, force-push или переписывание `main` без явного запроса владельца.
- Перед push: `git diff --check`, `pnpm run check:all`, проверка migration history и чистый `git status`.
- Новая клиентская функция, зависящая от schema/RPC, включается только после применения совместимой миграции.
- Breaking database contract разворачивай поэтапно: additive migration, совместимый client deploy, затем enforcement/cleanup migration.
- Массовая очистка данных разработки выполняется только через `api/admin.js`, серверный `service_role`, точную фразу подтверждения и RPC `admin_cleanup_development_data`; никогда не вызывай этот RPC из браузера.
- Production deploy считается завершённым только после push в `main`, HTTP-проверки Vercel и ручной/browser проверки изменённого пользовательского сценария.

## 18. Критические ограничения

- Не доверяй клиенту: весь клиентский JavaScript и anon key публичны.
- Не выполняй прямые client writes в `ratings`, `player_ratings`, `rating_likes` или `rating_comments`.
- Не обращайся из клиента к `chat_messages`, `direct_conversations`, `direct_messages` или messaging RPC: домен закрыт.
- Не разрешай клиенту создавать/удалять notifications или менять в них что-либо кроме `read`.
- Не раскрывай `users.email`, `users.is_admin` или `users.invite_code` через общий public select; служебные счётчики выдавай только в уже разрешённом read-only наборе полей и никогда не разрешай клиенту их изменять.
- Футбольные изображения всегда optional. Используй только `FBZMedia` и связанные `media_assets`: `verified` или узкий `identification` для API-Football club_logo на точном `media.api-sports.io/football/teams/<id>.png`. Второй статус обозначает использование для идентификации клуба по запросу владельца, не подтверждённую лицензию. `unknown`, `restricted`, `disabled`, deprecated `crest_url`/`photo_url` не показываются.
- Наличие provider URL не подтверждает лицензию. Не превращай `identification` в `verified`, не подключай этим путём фото игроков, hero imagery или rehosting. Provenance/terms и контроль отключения сохраняются. Пакеты эмблем требуют серверного preview/apply; internal IDs/legacy external_id неизменны. `club_provider_ids` и `club_emblem_batches` доступны только service_role. Для media на матчевой странице используется один bounded `get_club_marks` (96 IDs), optional fallback после 1.5 s.
- Не используй `live_chat_messages`, `support_tickets` и `referee_ratings` для новых функций: они не участвуют в текущих пользовательских сценариях и требуют отдельного решения по типам identity, grants и RLS.
- Сохраняй восстановленные baseline-миграции и проверяй, что чистая БД по-прежнему полностью разворачивается только из репозитория.
- Не обходи `api/admin.js` прямыми service-role запросами из браузера.
- Не ломай pretty deep links и обратную совместимость hash-ссылок, feature-loader, theme/accent contracts, mobile bottom navigation и E2E local-only guard.
- Локальная разработка, preview и CI не могут обращаться к production Supabase ref. Исключение `FOOTBAZED_ALLOW_PRODUCTION=1` допустимо только для явно контролируемой локальной диагностики и запрещено в CI.
- Не завершай работу без проверки безопасности данных, dark/light themes, desktop/mobile layout и автоматических тестов, соответствующих риску изменения.
