# Автоматическое обновление матчей

Основной планировщик — Supabase Cron `footbazed-match-results`. Минутное задание
вызывает `private.dispatch_match_sync()`. На минутах 0–5 каждого 15-минутного
интервала оно по очереди запрашивает PL, PD, BL1, SA, FL1, CL. Остальные минуты —
без сетевого запроса. Одна лига проверяется раз в 15 минут, не шесть одновременно.
Работа зависит от доступности БД, pg_net и Vercel; бесплатный источник по-прежнему
может задерживать счёт. Это не гарантия LIVE.

Резервный workflow `Automatic match results` запрашивает шесть турниров football-data.org
(PL, PD, BL1, SA, FL1, CL) на 7, 22, 37 и 52 минуте каждого часа.
GitHub может задержать или пропустить запуск; бесплатный источник отдаёт результаты
с задержкой. Это не гарантия LIVE или обновления ровно раз в 15 минут.

Каждый запуск обрабатывает интервал UTC от двух дней назад до семи дней вперёд.
Старые незавершённые матчи требуют ручного импорта через админку.
Между турнирами выдерживается 10 секунд. При HTTP 429 запуск прекращается.
Составы и эмблемы автоматически не импортируются.

## Безопасность

`api/sync-results-db` принимает только production POST. База генерирует случайный
256-битный пропуск для одной лиги, сроком три минуты. В private.match_sync_tickets
сохраняется только SHA-256; исходное значение находится лишь в кратковременной
закрытой очереди pg_net и передаётся по HTTPS на фиксированный адрес Vercel.
Service-only invoker RPC атомарно удаляет пропуск при проверке. Повтор, чужая лига,
просроченный или неизвестный пропуск отвергаются. Даже service_role не может
вызвать dispatcher или вставить пропуск. Нет постоянного общего секрета.
Private таблица недоступна anon/authenticated. В hosted Supabase объекты net
принадлежат supabase_admin, и обычный postgres не может отозвать их платформенные
PUBLIC grants. Защита очереди на HTTP-границе опирается на отсутствие net среди
exposed schemas: production probe должен получить PGRST106/406. Не добавлять net
в Data API/GraphQL и не создавать публичные SQL/RPC-обёртки чтения очереди.
Операторы с прямым SQL-доступом остаются доверенными. Не выводить заголовки
очереди, параметры RPC с исходным пропуском и полные HTTP-запросы в диагностику.

Endpoint `/api/sync-results` принимает только POST в Vercel Production.
Подпись RS256 проверяется по фиксированному JWKS GitHub; обязательны точные
repository/owner IDs, main, имя workflow, audience, короткий срок токена и
событие schedule/workflow_dispatch. Токены и ключи не записываются в журнал.
GitHub не хранит ключи поставщика или Supabase.

Service-only RPC `claim_automatic_match_sync` использует блокировку транзакции,
уникальную пару турнир/run_id и десятиминутный интервал между запусками.
Повтор того же run_id не импортирует данные заново: для ручного повтора создайте
новый workflow_dispatch после завершения интервала.

## Проверка и обслуживание

1. GitHub → Actions → Automatic match results → Run workflow → main.
2. Проверьте результаты всех шести турниров в логе задания.
3. FOOTBAZED → Админка → Обзор: голубой индикатор появляется только после
   успешной проверки всех шести турниров не более 45 минут назад.
4. Админка → Журнал: запуск, успех и ошибка сохраняются отдельно для каждой лиги.
   Ноль обработанных матчей допустим: на выбранные даты может не быть игр.
5. При длительной задержке проверьте Supabase → Cron → footbazed-match-results,
   затем безопасные поля net._http_response (status_code, timed_out, created).
   Успешное SQL-задание подтверждает только постановку HTTP-запроса в очередь;
   результат импорта подтверждает auto_sync_succeeded для каждой лиги.
   Для резервного запуска проверьте Actions. GitHub может отключить scheduled
   workflow публичного репозитория после 60 дней без активности.

Остановка основного расписания: Supabase → Cron → footbazed-match-results → выключить.
Остановка резерва: Actions → Automatic match results → меню ⋯ → Disable workflow.
Для отката сначала остановите workflow, затем откатите код через обычный PR.
Аддитивные индексы и неиспользуемый service-only RPC можно оставить:
они не меняют существующие пользовательские данные.

Перед выпуском нужны миграция, pgTAP, полный CI, подтверждение production SHA
и успешный реальный запуск. Наличие файла расписания само по себе не означает,
что автоматическая синхронизация уже работает.

## Включение после публикации

Миграции не создают активных заданий, поэтому reset/CI не отправляет запросов
в production. Только после проверки точного production SHA и отказа гостевого
доступа владелец базы выполняет в production:

Перед включением выполнить `node scripts/check-scheduler-boundary.mjs`: запрос
`Accept-Profile: net` обязан быть отвергнут без чтения содержимого очереди.

```sql
select cron.schedule('footbazed-match-results','* * * * *',
  'select private.dispatch_match_sync();');
```

Проверить успешный импорт всех шести лиг и второй цикл через 15 минут.
GitHub может пропускать импорт из-за общего 10-минутного cooldown — это ожидаемо.
История cron хранится отдельно от постоянного журнала импорта; периодически
удалять только старые job_run_details этого задания согласно политике хранения.
