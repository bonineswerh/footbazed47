# Media architecture

## Текущее состояние

Production может работать без реальных эмблем и фотографий. На момент введения слоя ни один внешний футбольный asset автоматически не считается разрешённым. Техническая готовность media layer не означает наличие лицензированных файлов.

## Поток asset

1. Provider или администратор создаёт кандидат с provenance и `usage_status=unknown`.
2. Проверяются источник, конкретная лицензия, коммерческое использование, attribution, срок и территория.
3. Неподходящий файл получает `restricted` или `disabled`.
4. Только доказуемо разрешённый файл получает `verified`, `verified_at`, `verified_by` и может быть связан с сущностью.
5. RLS и RPC отсекают все остальные статусы до frontend.

Нельзя менять `unknown` на `verified` только потому, что provider возвращает URL или логотип доступен публично.

## Frontend

`FBZMedia.resolveAsset` принимает только HTTPS, ожидаемый тип и `verified`. `FBZMedia.visual` в остальных случаях показывает initials и детерминированную пару цветов. Club, Player и Competition продолжают работать без изображения; broken image и пустой layout не являются допустимым fallback.

## Provider interface

Provider регистрируется явно через `{id, resolve(request)}`. Автоподключённых providers нет. Результат integration adapter обязан сохранять исходный URL и условия, не может объявлять права сам и по умолчанию остаётся `unknown`.

## Ограничения и gaps

- Нет подтверждённых соглашений с клубами, лигами, игроками, фотографами или правообладателями.
- Нет автоматического workflow юридического review или admin UI для подтверждения assets.
- Нет production bucket для domain media; Storage сейчас используется только для пользовательских аватаров.
- Deprecated provider URLs в старых строках не мигрируются автоматически, поскольку происхождение и права не доказаны.

Следующий этап media начинается с выбранного договорного источника и review конкретного набора файлов, а не с массового импорта URL.

## API-Football: подключение эмблем 30.09.2026

Владелец прямо попросил увидеть эмблемы API-Football на сайте. Для такого использования принят отдельный узкий статус `identification`: клубные эмблемы из ответа `/teams`, только HTTPS `media.api-sports.io/football/teams/<provider_id>.png`, без копирования в Storage и без объявления подтверждённой лицензии. Это продуктовая политика идентификации по официальным условиям источника, не юридическое заключение о правах на конкретную эмблему. `license_name`, `license_url`, `verified_at`, `verified_by` остаются пустыми; metadata сохраняет source ID, имя/страну, сезон/турнир, условия и `rights_status=not_verified`. Любой другой тип/источник остаётся `unknown`. [Условия API-Football](https://www.api-football.com/terms).

Сервер получает один ограниченный набор клубов для выбранной лиги/сезона. Сопоставляет country + нормализованное имя или явный alias; неоднозначность и конфликт provider mapping пропускаются. В staging сохраняются внутренний ID, legacy external_id и предыдущая media-связь. Применение — отдельный service-only RPC, целиком в транзакции с блокировкой и проверкой неизменности identity. Старые ID, оценки и составы не меняются. Не перезаписываются чужие/отключённые assets. Повтор apply идемпотентен. Отмена восстанавливает before images; отказывается менять клуб, обновлённый после применения. Audit создаётся внутри той же транзакции.

`is_displayable_media_asset` — единый SQL-предикат для RLS и существующих aggregate RPC. `get_club_marks` отдаёт минимальные публичные DTO за один запрос на страницу, не более 96 IDs. Frontend сохраняет размеры знака, object-fit contain, lazy loading, no-referrer и initials при сетевой ошибке; задержка optional media не блокирует страницу дольше 1.5 s. Секрет API-Football браузеру не нужен.

Отключение: `usage_status=disabled` закрывает asset через RLS/RPC; фронтенд переходит на initials. Для последнего неизменённого пакета доступно «Отменить подключение» в админке. Фотографии, медиахранилище и импорт каталога остаются отдельными этапами.
