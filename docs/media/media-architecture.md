# Media architecture

## Текущее состояние

Production может работать без реальных эмблем и фотографий. На момент введения слоя ни один внешний футбольный asset автоматически не считается разрешённым. Техническая готовность media layer не означает наличие лицензированных файлов.

## Поток asset

1. Provider или администратор создаёт кандидат с provenance и `usage_status=unknown`.
2. Проверяются источник, конкретная лицензия, коммерческое использование, attribution, срок и территория.
3. Неподходящий файл получает `restricted` или `disabled`.
4. Только доказуемо разрешённый файл получает `verified`, `verified_at`, `verified_by` и может быть связан с сущностью.
5. RLS и RPC отсекают все остальные статусы до frontend.

Нельзя менять `unknown` на `verified` только потому, что provider возвращает URL или логотип доступен публично.

## Frontend

`FBZMedia.resolveAsset` принимает только HTTPS, ожидаемый тип и `verified`. `FBZMedia.visual` в остальных случаях показывает initials и детерминированную пару цветов. Club, Player и Competition продолжают работать без изображения; broken image и пустой layout не являются допустимым fallback.

## Provider interface

Provider регистрируется явно через `{id, resolve(request)}`. Автоподключённых providers нет. Результат integration adapter обязан сохранять исходный URL и условия, не может объявлять права сам и по умолчанию остаётся `unknown`.

## Ограничения и gaps

- Нет подтверждённых соглашений с клубами, лигами, игроками, фотографами или правообладателями.
- Нет автоматического workflow юридического review или admin UI для подтверждения assets.
- Нет production bucket для domain media; Storage сейчас используется только для пользовательских аватаров.
- Deprecated provider URLs в старых строках не мигрируются автоматически, поскольку происхождение и права не доказаны.

Следующий этап media начинается с выбранного договорного источника и review конкретного набора файлов, а не с массового импорта URL.
