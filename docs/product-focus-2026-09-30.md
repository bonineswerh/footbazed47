# Следующий этап FOOTBAZED: футбольная история

Основание: независимый аудит, переданный владельцем 30 сентября. Документ является набором гипотез, кроме явного продуктового решения об отказе от чатов. Базовый main: 15f8af7. Не объединяем удаление домена, изменение контрактов оценки и большой redesign в один релиз.

## Проверка гипотез и решения

- Пункты 1, 39, 41–45: messaging действительно отдельный необязательный домен. Полная карта ниже. Первый выпуск закрывает клиентские поверхности, доступ к данным и вложениям. Данные сохраняются.
- Пункты 2–3, 9, 18–23, 27: оценки, рецензии, реакции, комментарии, дружба и дневник уже существуют независимо от messaging. Оставляем их. Навигацию «Друзья» не удаляем механически: принятие заявок и сравнение профилей работают без чата. Следующий продуктовый шаг — улучшение отображения рецензий и личной истории.
- Пункты 4–8, 35: игрок уже оценивается через стилизованный range с aria-valuetext, клавиатурой, сбросом и состоянием без оценки (`js/ratings.js`). Общая оценка остаётся целой 1–10 по контракту БД. Примеры 8.4/8.7 из аудита не являются разрешением менять личную оценку на дробную; десятичные значения нужны для средних. `FBZDomain.ratingPresentation/ratingTone` уже задают единый смысл цвета. Новый параллельный контракт не нужен. Следующий этап: общая визуальная шкала матча/игрока и числовая типографика; сохранение атомарного RPC, unset и best-player invariants обязательно.
- Пункты 7–8, 19, 24–26: распределение и личное сравнение уже есть на матче (`matchDistributionMarkup`, `.md-rating-comparison`). Улучшать представление, а не добавлять дубликат. Сравнение с друзьями и история игрока требуют отдельной проверки приватности и объёма выборки. Отсутствующие данные нельзя выдавать за 0 или придумывать тренд.
- Пункты 10–16, 28: проблема фильтров подтверждена. `FBZExplore.populate` формирует общий список строк teams/leagues; `get_football_statistics` принимает текстовые параметры; одинаковые поля используются для разных типов. Серверная фильтрация, ограниченная выдача, валидация дат, отмена устаревшей выдачи уже есть. Следующий самостоятельный этап: canonical competition/club IDs, зависимый поиск клуба, контекстные фильтры, chips, мобильная панель и URL-состояние. Миграция должна предшествовать новому клиентскому контракту. `/discover` уже canonical; полный rename statistics не оправдан.
- Пункты 17, 29: глобальный поиск уже ленивый, с клавиатурой, debounce и историей. Сохраняем. Принципы внешних сервисов — ориентир, не копирование оформления или обязательная новая зависимость.
- Пункты 21, 40, 42: комментарии имеют отдельные лимиты/RPC, escaping и удаление автором; friendship и admin тоже независимы. Чаты не требуют новой платформы модерации. Редактирование комментариев/reporting — будущая проверка, не заявленная готовая функция. Прогнозы остаются вторичными; их удаление аудит не требует.
- Пункты 30–34, 36–38, 46–48: rewrite и увеличение бюджета отклонены. Существующие CSP, SEO, Axe, cross-browser и theme contracts сохраняются. RUM требует решения о данных/хранении, физические устройства отдельно от эмуляции. Запас 15–20% стартовых assets пока не достигнут: удаляемый messages.js уже был lazy. До изменения 504796 bytes, после удаления домена 496626 bytes в локальном контрольном прогоне; бюджет прежний 512000 bytes. Нельзя выдавать эти цифры за production RUM.

## Карта зависимостей messaging

- `app.js`: match-chat route/state/read/send/edit; lazy messages loader; forwarding bridge. Удалены. Старый hash `/match/:id/chat` ведёт к матчу через replaceState. HTTP `/match/:id/chat` отдаёт 410/noindex; функциональность чата не открывается.
- `index.html`, `js/shell-actions.js`: match-chat page и direct overlay/composer/media/voice bindings. Удалены из HTML и registry.
- `js/messages.js`, `css/messages.css`: direct conversations, media upload, signed URLs, recorder, realtime, session reset. Файлы удалены; static check запрещает их возвращение.
- `js/matches.js`, `js/community.js`, `js/profile.js`, `js/feed.js`: chat CTA и пересылка оценок. Удалены; переходы в матч/профиль, оценки, реакции и комментарии сохранены. Подтверждение удаления друга теперь объясняет последствия для ленты друзей.
- `js/auth.js`: messaging session hook удалён; остальные session guards сохранены.
- `styles.css`, `css/typography.css`: удалены match-chat и cmsg-стили, ссылка на direct composer.
- `vercel.json`: `microphone=()`, `media-src 'none'`; websocket origin удалён из connect-src. Единственная production realtime publication была `direct_messages`. HTTPS Supabase нужен для остальных данных и аватаров.
- SQL API: семь chat/direct RPC закрываются для PUBLIC/anon/authenticated. Таблицы conversations/messages/chat остаются архивом; grants отозваны, добавлены restrictive deny policies. Прямой доступ не может заменить отключённый UI.
- Storage: bucket `chat-media` и объекты сохранены; пользовательские policies сняты, отдельный restrictive deny закрывает чтение, загрузку, изменение, удаление. Ранее выданные signed URLs живут до истечения их TTL (старый клиент использовал 3600 секунд); отзыв policy не обещает мгновенную инвалидизацию таких URL.
- Realtime: direct_messages исключается из publication. Другая функциональность на subscriptions не опиралась.
- Уведомления: существующий клиент поддерживает friend_request/like/comment, отдельной отправки message notifications не найдено. Переписывание taxonomy не нужно.
- Admin cleanup всё ещё ссылается на архив сообщений и rating_id: функции/FK не удаляем. Никакой очистки production в этом этапе нет.
- `supabase/tests`: сценарии разрешённого messaging заменены отрицательными проверками anon/участника беседы; сохранность данных проверяется отдельно. Тесты rating/friend/comment не удалены.
- Browser tests: удалены только сценарии выведенных чатов. Добавлены отсутствие CTA/assets, HTTP 410, старый hash, сохранение review comments и запрет микрофона/media. Smoke проверяет живой маршрут 410.

## Данные и развёртывание

Read-only inventory до изменения: 3 личные беседы, 17 сообщений, 7 storage objects; match chat пуст. Тела сообщений, пути файлов и личные данные не выгружались в репозиторий. Ничего из содержимого не удаляется; схема/права до изменения воспроизводятся по предыдущим миграциям. Destructive cleanup и срок хранения архива — отдельное решение владельца с backup, не часть этого выпуска.

Истории local/remote сверены по именам: 31 соответствующая миграция, у последних четырёх уже существовали разные timestamp identifiers. Не переписываем применённую историю. Новая миграция создана Supabase CLI и изменяет только доступ/publication/policies, не форму данных/RPC и не TypeScript-контракт.

Порядок: проверить клиент и отрицательные SQL-тесты → опубликовать совместимый клиент → применить enforcement → проверить фактические права/данные/advisors → production smoke. У старого открытого клиента записи будут отклоняться сервером.

## Rating Experience: реализованный следующий выпуск

- Общая шкала матча/игрока использует native range с единым собственным оформлением, областью взаимодействия 48px, keyboard arrows/Home/End, явным подтверждением начальной 5 через Enter/Space, `aria-valuetext` и reduced motion. Личная оценка остаётся целой 1–10; исходный thumb на 5 не создаёт оценку и не попадает в payload.
- Для матча сохранён точный выбор числовой кнопкой; шкала и кнопки синхронизированы. Сброс возвращает unset и не позволяет продолжить без оценки. Выбор стороны болельщика остаётся обязательным. RPC и best-player invariants не изменены.
- Главная оценка поднята выше выбора стороны. Числа отображаются Onest 650 с tabular numerals; `/10` отделён и меньше основного значения. 9 и 10 сохраняют голубую семантику. Выделяется выбранная кнопка, а не все предыдущие числа. Название 10 — «Исключительно».
- Первый шаг компактнее на desktop; его действия закреплены внизу scrolling dialog. Переходы между шагами возвращают scroll к началу. Close и player editor actions имеют минимум 44px.
- На телефонах до 620px вместо тесного поля используется список игроков с полными именами, позициями и читаемыми оценками; desktop сохраняет поле и группировку по позициям. Исправлен подтверждённый light-theme конфликт белых цифр на белом фоне. Score badge использует те же semantic tokens в обоих представлениях.
- `css/ratings.css` загружается только при открытии редактора. Удалены старые range/score/quick-choice styles и конфликтующие light overrides из общего CSS. Постоянный `openRate` wrapper вызывает `FBZRatings.open` после JS **и** CSS; частичная ошибка CSS не позволяет следующему нажатию обойти loader. Повтор проверяется без дублирования JS.
- Новые regression scenarios проверяют unset/5, синхронизацию шкалы/кнопок, сброс best-player vote, CSS retry, мобильные действия и имена, сохранение payload. Cross-browser сценарий дополнен шкалой матча; Axe проверяет оба шага; performance проверяет отсутствие rating assets на главной.

Эта реализация не добавляет вымышленные сравнения с друзьями, данные сезонов или дробные личные оценки. Следующие самостоятельные задачи — контекстные фильтры обзора и дальнейшая работа с рецензиями/дневником.

Итоговая локальная проверка выпуска: `pnpm run check:all` — 60 unit + 193 browser scenarios успешно; `pnpm run build` и `git diff --check` пройдены. Восемь визуальных эталонов редактора обновлены после осмотра и проверены обычным полным прогоном без повышения допусков. Axe проверяет полностью открытое окно после готовности формы; keyboard scenario дожидается enabled control. Локальный performance sample: 492028 bytes стартовых JS/CSS, LCP 228ms, CLS 0.0377; это не production RUM и не проверка физического телефона. Запас 15–20% остаётся отдельной задачей. Production проверяется после публикации этого выпуска.
