# Этап 3: второй фактор администратора

F05: реализация защиты и подключения. Полное закрытие пункта требует подключения реального аутентификатора владельцем и проверки авторизованного чтения после подключения. Агент не получает QR, ключ или одноразовый код владельца.

## Изменение границы доступа

Все пути `/api/admin` по-прежнему проверяют подпись токена через Supabase Auth и `public.users.is_admin`. После этого `server/security/admin-session.js` проверяет issuer проекта, audience/role, sub, expiry и session_id. Узкий service-only RPC сверяет наличие и срок живой сессии, её AAL и принадлежность действующего подтверждённого TOTP. Даже неистёкший AAL2 JWT не даёт доступ после отзыва сессии/фактора/права администратора. Ошибка проверки закрывает доступ.

Для административных чтений, импорта, модерации и операций с поставщиками требуется AAL2. Начальная AAL1 сессия администратора допускает только `GET action=access_status`: один флаг о необходимости MFA, без персональных данных, каталога, квоты и жалоб. Очистка требует подтверждения TOTP в последние пять минут; password AMR и будущая дата не подходят. Прежние фразы подтверждения, подготовленный каталог и серверные ограничения сохраняются.

## Интерфейс

Модуль безопасности загружается только в `/admin`. Первое подключение выполняется через Supabase SDK: пользователь сам сканирует QR или вводит ключ в приложении, затем вводит шесть цифр на сайте. Новый фактор создаётся лишь по кнопке, а не при открытии раздела. Незавершённый черновик удаляется только явным действием пользователя; подтверждённый фактор здесь не удаляется. Вход через действующий фактор поддерживает выбор устройства, неверный код и повтор.

Общие FBZOverlay обеспечивают blur, клавиатуру, Escape и возврат фокуса. QR отображается в изображении, SVG не вставляется как HTML. Код и ключ очищаются при закрытии, переходе и смене сессии; нет собственного хранения credentials. Поздний ответ другой сессии не открывает окно. После подтверждения очистка не возобновляется сама: пользователь повторяет её вручную. Русский и английский интерфейсы сохраняют один контракт.

## Совместимое обновление БД

Один новый readonly RPC, без изменения таблиц, существующих policies, каталога и настоящих факторов. Файл создан CLI `migration new` в отдельной папке из-за ошибки CLI 2.114.0 с существующим каталогом migrations; после применения MCP версия имени согласована с реальной историей: **20261008204539**. Предыдущее состояние — отсутствие функции, raw SELECT Auth sessions для service_role запрещён. Эти grants не менялись. Контракт типов получен из действующей БД и нормализован штатным скриптом.

На production выполнены проверки временных пользователей/сессии/фактора внутри BEGIN/ROLLBACK: реальный service path, запрет anon/authenticated, чужой actor, отсутствующая/просроченная сессия, AAL1, неподтверждённый фактор и отозванное право администратора. Отдельно подтверждено отсутствие временных пользователей после отката. pgTAP с 14 проверками предназначен для clean CI database; расширение pgTAP в production не устанавливалось. Security/performance advisors до/после не добавили предупреждений. Существующая видимость публичного каталога и ограниченных readers требует отдельной оценки; предупреждение о защите от скомпрометированных паролей остаётся открытым.

## Проверки и выпуск

Обязательны pnpm check:all, SQL clean reset/type comparison/pgTAP и secret scan в CI. MFA E2E используют только локальный mock: телефон/desktop, обе темы, QR/manual, retry, no auto replay, очистка credentials, смена пользователя, отказ Auth, небезопасный QR и EN. Настоящие factor секреты не участвуют в автоматических тестах.

Выпуск идёт через feature/admin-mfa и защищённый PR; затем отдельный main CI, production gate, release.json, публичные HTTP-проверки и браузерная проверка AAL1 экрана. Результаты и точные SHA/run IDs сохраняются в reports/full-audit-2026-10-08/stage-3 вне публичного bundle.

## Действие владельца после публикации

Откройте `/admin` → «Продолжить» → «Подключить». Добавьте FOOTBAZED в собственный аутентификатор, подтвердите код на сайте и сохраните резервную копию средствами приложения. После подтверждения другие сеансы аккаунта завершаются средствами Supabase Auth. Ключ, QR, пароль и код не отправляйте в чат. Потеря устройства без копии требует восстановления владельцем проекта через Supabase и проверки личности; пароль не создаёт исключение из MFA.

Открыты: реальное подключение владельца (F05), автоматическая актуализация данных (F01), ограничения поставщика (F02), отдельный staging/проверенный rollback (F03), сбор runtime ошибок и контроль свежести (F06). Этот этап не объявляет полный аудит завершённым.
