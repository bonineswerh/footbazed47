# Архитектура FOOTBAZED

## Runtime

FOOTBAZED остаётся History API SPA на HTML, CSS и обычном JavaScript. Supabase предоставляет Auth, Postgres, RLS и RPC. Vercel обслуживает статику, runtime-конфигурацию, sitemap, первоначальные публичные metadata и защищённую admin function.

Маршруты `/club/:id`, `/player/:id`, `/competition/:id`, `/match/:id` и `/profile/:id` обслуживает `api/page.js`, заполняя metadata в собранном `dist/index.html`. Общие правила находятся в `js/seo.js`. Только публичные футбольные сущности читаются с publishable key; профиль/чат получают неперсональный noindex shell без общего кэша. Это не полный SSR. Локальный E2E-сервер отдаёт оболочку для тех же путей; серверный HTML отдельно проверяется unit-тестами и `scripts/smoke-public.mjs` после публикации.

## Границы модулей

- `app.js`: shell и маршрутизация.
- `js/feature-loader.js`: общий загрузчик ленивых JS/CSS, таймауты и повтор после ошибок; готовый namespace не заменяет готовность стилей.
- `js/auth.js`: сессия и профиль.
- `js/entities.js`: клубы, игроки, турниры.
- `js/media.js`: единственная клиентская точка разрешения domain media и fallback UI.
- `js/home.js`: авторизованный dashboard и избранные клубы.
- `js/search.js`: глобальный поиск и переходы.
- `js/data.js`: общие пагинированные RPC.
- `js/community.js`: списки друзей, заявки и поиск пользователей.
- `js/notifications.js`: уведомления, общий счётчик непрочитанных и подтверждённые сервером отметки чтения.
- `js/profile-editor.js`: форма профиля, нормализация аватара и сохранение.
- `js/profile.js`: просмотр профиля, видимая выборка оценок, фактические показатели и дневник участия.
- `js/share.js`: экспорт Canvas в PNG 1200×800; шрифт Onest загружается до рисования.

`entities`, `feed`, `ratings`, `messages`, `search`, `community`, `profile`, `profile-editor`, `share` и `admin` загружаются лениво. Уведомления догружаются после входа. Стили самостоятельных экранов подключаются тем же feature-loader. `js/rating-loader.js` сохраняет публичный вызов `openRate()`, но не загружает полный модуль до явного действия пользователя. MediaResolver загружается до доменных экранов, но не выполняет сеть и не блокирует core.

## Визуальная система матчей

`css/match-editorial.css` задаёт общую иерархию счёта, названий команд и статуса для главной, календаря и страницы матча. Главный блок выбирает live, будущий или завершённый матч из уже полученной выборки `FBZData.getMatchesPage()`; отдельный запрос для оформления не нужен. Декоративные монограммы и линии поля создаются в CSS, поэтому блок работает без непроверенных логотипов и фотографий. Карточки ленты подхватывают ту же иерархию, сохраняя семантические цвета пользовательских оценок. Тёмная и светлая темы используют действующие переменные оформления.

## MediaProvider

`FBZMedia.registerProvider()` и `resolveFromProvider()` образуют выключенную по умолчанию границу будущих интеграций. Provider не считается разрешённым источником из-за наличия API. Он может вернуть только кандидат с provenance и исходным статусом `unknown`; публикация требует отдельной проверки и записи `verified` на сервере.

Frontend отображает URL только когда RPC вернул asset с совпадающим `asset_type`, `usage_status=verified` и HTTPS URL. Во всех остальных состояниях используется deterministic fallback.

## Надёжность

Загрузка избранных клубов является дополнительной: shell авторизованного пользователя рендерится после обязательного `get_my_profile`, затем favorites догружаются без повторного построения навигации. Это исключает гонки панелей и не блокирует вход при временной ошибке дополнительного RPC.

`FBZData.setSessionUser()` изолирует кэш и незавершённые чтения между аккаунтами. Auth вызывает сброс доменных модулей и событие `fbz:session-change` на `window`. Обновление токена того же пользователя не уничтожает действующий кэш. Инвалидация после записи не позволяет более старому чтению снова наполнить кэш устаревшими данными.

Асинхронные действия захватывают идентификаторы пользователя, сущности и версии экрана до запроса. Ответ старого маршрута не должен менять новый экран. Повторная отправка блокируется; ошибка сохраняет введённый текст. Личный чат хранит черновики отдельно для собеседников и останавливает микрофон при закрытии.

Списки друзей показывают по 24 записи, поиск — до 12, панель уведомлений — последние 20. Общий счётчик непрочитанных считается отдельным ограниченным по пользователю запросом без передачи всей истории. Текущий предел выборки связей дружбы — 1000; для дальнейшего роста нужен серверный курсор, а не увеличение клиентского лимита.

Для ручной проверки без настоящих аккаунтов: `node scripts/serve.mjs --demo`, затем локальная страница с `?__e2e=1`. Деморежим использует те же фикстуры, что E2E, не выдаёт ключи и запрещён в CI/Vercel. Обычный сервер остаётся защищён от случайного подключения к production.

## Типографика и дневник

`css/typography.css` подключается после общего и editorial CSS. Onest обслуживает кириллицу и основной интерфейс; Bebas используется для бренда и отдельных крупных чисел. Общие токены задают подписи 12 px, компактный текст 14 px и основной текст 16 px при стандартном размере шрифта браузера. Шрифты уже self-hosted, новых сетевых зависимостей нет.

`FBZDomain.profileActivity(count)` возвращает нейтральную формулировку количества оценённых матчей и следующую отметку. Владелец видит личный прогресс; чужой профиль — только факты. Лайки и друзья не участвуют. Правило не создаёт новые права, роли, поля БД или миграции. Прежние LEVELS и FBZ Score удалены. Аналитика по последним оценкам явно обозначает размер видимой выборки.

Профиль и экспорт подключаются только при открытии. Глобальные loadProfile/openShare сохраняют совместимость и проверяют пользователя и маршрут после загрузки модуля. Тесты фиксируют отсутствие этих assets на стартовой главной, корректность русского склонения, границы прогресса, ошибки и поздние ответы.

## Цвета матчей и оценок

`ratingTone` — единственный источник диапазонов: 1–3 low, (3,7) mid, [7,9) high, [9,10] elite. Таким образом, девятка и десятка одинаково голубые в формах, ленте, средних оценках, распределениях и PNG. Светлая тема затемняет голубой для контраста. Значение счёта матча и количество оценок не являются рейтинговыми оценками.

`clubColor` сопоставляет точные нормализованные имена с курируемыми спокойными оттенками, `matchPaletteStyle` возвращает только безопасные переменные двух цветов. Неизвестный клуб получает нейтральный оттенок. `css/club-palettes.css` использует переменные в календаре, главном матче, странице матча и ленте, без анимации градиента. Цвета клубов не переопределяют семантические цвета оценок.
